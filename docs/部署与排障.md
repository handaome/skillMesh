# 部署、备份与排障

备份与恢复验证、身份源配置、生产前必须处理的事、受限网络下访问 GitHub、端口与常见故障。
本地起环境见 [README](../README.md#快速开始)。

## Docker Compose 路线

仓库根目录的 `docker-compose.yml` 把 PostgreSQL、MinIO、API、前端四个服务编排在一起，
适合要一个自包含环境、或不想在本机装数据库的场景。

```bash
cp .env.example .env      # 至少填 SM_DB_PASSWORD 与 SM_JWT_SECRET
docker compose up -d --build
docker compose ps
```

与本机原生进程路线**互斥** —— 两者抢同一批端口：

| 服务 | compose | 原生脚本 |
| --- | --- | --- |
| PostgreSQL | 容器内 5432 | 不起（连 `.env` 里 `SM_DB_URL` 指向的远程实例） |
| MinIO | 127.0.0.1:9100 / 9101 | `start.sh`，同端口 |
| API | 127.0.0.1:8080 | `./mvnw spring-boot:run`，同端口 |
| 前端 | 127.0.0.1:5174 | `pnpm dev`，同端口 |

切到 compose 前先 `bash infra/scripts/stop.sh`；切回原生路线先 `docker compose down`。

两处差异要注意：

1. **令牌密钥不同**。compose 的 api 服务读 `SM_JWT_SECRET`；原生路线读同一个变量，但值在各人自己的 `.env` 里。
2. **数据库不同**。compose 起的是本地 PostgreSQL；原生路线连远程实例，测试库与应用库的隔离规则见 README。

## 改 schema 的三种方式

Flyway 的历史表记着每个迁移的校验和。**改了已经应用过的迁移文件，校验和就对不上**，
应用启动会直接失败（`Found applied migration with checksum X but resolved checksum Y`）。

- **开发库**（数据可以丢）：改迁移文件后清库重建 —— 用任意 PostgreSQL 客户端执行：
  ```sql
  drop schema public cascade;
  create schema public;
  ```

  下次启动时 Flyway 会重新建表。库里的数据全没了，开发库无所谓。
- **有数据的库**：不要动旧迁移，另加一条新的 `V15__xxx.sql`。已应用过的迁移内容永远不改。
  版本号从 15 往后排的理由见下面那段提示；提交前跑一遍
  `bash infra/scripts/check-migrations.sh`，版本号用错的地方它会直接报出来。
- **历史被重写过、但表结构本身是对的**：跑 `flyway repair` 对齐历史，见下。

当前迁移链是 10 条：`V1__init.sql`（全量初始 schema，20 张表）、`V2__archived_slug.sql`、
`V3__installation_agent_freedom.sql`、`V4__skill_groups.sql`、`V5__local_accounts.sql`、
`V6__query_sort_indexes.sql`（三个排序键的索引）、
`V11__ensure_query_sort_indexes.sql`（同三个索引，带 `IF NOT EXISTS` 再补一遍）、
`V12__owner_status_sort_indexes.sql`（归档列表与按状态过滤的安装列表这两条路径的索引）、
`V13__drop_scanning_status.sql`（版本状态里的 `scanning` 删掉——那一档从来没人到过）、
`V14__partition_audit_events.sql`（审计表按月分区，过期整月分区直接 DROP）。
正式环境一旦有数据，就只能走「加增量迁移」这条路。

### 迁移链被整体重写过：flyway repair

`e39692f` 那次把旧的 V1~V10 删光，换成新的 V1 并**从头复用版本号**。
按旧链建过表的库，`flyway_schema_history` 里记的还是旧历史，
跟当前文件一对就报：

```
Migration checksum mismatch for migration version 1..5
```

**应用起不来**，不是警告。动手前先分清是哪种情况：

- **表结构与当前迁移文件一致**，只是历史表记错了（checksum、描述、类型对不上）
  → 跑 `flyway repair`。它把历史表里已应用迁移的校验和与描述对齐到当前文件，
  **不动 schema、不动数据、不重跑迁移**。
- **表结构也不一致**（少表、少列） → repair 修不了，得清库重建或写增量迁移补差异。

repair 的命令（凭据从根目录 `.env` 读，别写进命令行历史）：

```bash
cd apps/api
mvn org.flywaydb:flyway-maven-plugin:11.7.2:repair \
  -Dflyway.url="$SM_DB_URL" -Dflyway.user="$SM_DB_USER" -Dflyway.password="$SM_DB_PASSWORD" \
  -Dflyway.locations=filesystem:src/main/resources/db/migrations
```

**repair 之后直接启动应用就行**，不用再手工改历史表。repair 做完三件事：

- 本地有对应文件的旧行（v1~v6）：校验和与描述被改写成当前文件的，等于「就当它跑过了」。
- 本地没有对应文件的旧行（v7~v10）：标成已删除（`type` 写成 `DELETE`），校验时不再理会。
- 本地多出来的版本号（V11、V12、V13、V14）：正常待执行，启动时跑掉。

schema 版本号停在旧的最大值（10）。当前链的最大版本是 14，比它大——
版本号比当前高的迁移还没跑，等它跑掉就正常了。
> V1 现在是全量 schema，旧链 V6~V10 的 DDL（`submitted_at`、`idx_skills_id_text`、
> `base_revision`、`skill_recycle_files`、邀请索引与约束收紧）它都已经包含了，
> 所以「旧链跑过」与「当前 V1 建出来」的表结构是一样的。

**为什么还有一条 V11**：旧链的 v6 行会被 repair 改写成当前 V6 的校验和，
Flyway 于是认为 V6 已经跑过——而 V6 的三个索引其实一个都没建。
V11 用 `CREATE INDEX IF NOT EXISTS` 把这三个索引再补一遍：
建过就跳过，没建就建上。老库上靠它补齐，新库上它是空操作。
它也不能改：改了校验和又对不上。

**别在应用起来之后再改历史表**。迁移历史被手工删过，下次启动那条迁移会重跑；
V6 里的 `CREATE INDEX` 没有 `IF NOT EXISTS`，索引已经建着就会报 42P07，
应用起不来。要重来就趁应用没起来时改。

> 新加迁移时避开旧链用过的版本号。旧链用过 V1~V10（`e39692f` 之前），
> 当前链用到 V6、V11~V14。往后加迁移从 **V15** 往后排：
> V7~V10 旧链也用过，在没清过陈年行的库上撞上去就是 checksum mismatch。
> `bash infra/scripts/check-migrations.sh` 查的就是这件事：旧号、插队、重号、
> 命名不对都会报出来并以非 0 退出。旧号那一集是从 git 历史里查出来的，
> 换一条链也照样对，不用在这里手工维护清单。

**校验和跟行尾无关**：Flyway 按行算 checksum，CRLF 与 LF 算出来一样，
所以换机器 checkout 出的行尾不同并不是 mismatch 的原因。
`.gitattributes` 里锁 `*.sql text eol=lf` 只是为了让工作区不脏、diff 不变形。

## 备份与恢复验证

```bash
java -jar apps/api/target/skillmesh-api.jar --skillmesh.backup.dir=D:/backup/skillmesh
```

启动时导出一份备份：落在 `<目录>/<时间戳>/` 里，每张表一个 `db/<table>.ndjson`，每个对象在 `objects/` 下有一份拷贝，`manifest.json` 记行数、大小和 SHA-256。导完立刻自检一遍，把结果打进日志。

走 JDBC 和 MinIO SDK 而不是 `pg_dump` / `mc`——这两个 SDK 本来就在依赖里，备份时不用在每台机器上再装客户端。

**应用起不来的时候也能备份**：上面那条走的是应用启动（要过 Flyway 校验），
迁移历史对不上时应用根本起不来，备份也就跟着跑不了——而那恰恰是最需要备份的时候。
这时候用独立入口：

```bash
bash infra/scripts/backup.sh D:/backup/skillmesh
```

它绕开 Flyway，只要数据源与对象存储的连接。导出的落点与上面一样：
`<目录>/<时间戳>/`（一次导出一个目录，下一次不会把上一次的恢复点覆盖掉）。

它自己按 Maven 仓库拼 classpath，用的是本机的仓库位置。仓库不在默认的 `~/.m2/repository` 时，
把位置告诉它——写在根目录的 `.env` 里即可（脚本会加载 `.env`）：

```bash
MAVEN_REPO=D:/mavenRepository
```

找不到依赖时脚本会直接列出缺哪几个 jar 并退出，不会拿半截 classpath 去跑出一堆 ClassNotFound。

**定期备份有两种做法**：

一是由系统的 cron 调它（保留期该由运维策略决定）：

```bash
# 每天凌晨 3 点导一次，保留 30 天
0 3 * * * bash /path/to/skillmesh/infra/scripts/backup.sh /srv/backup/skillmesh >> /var/log/skillmesh-backup.log 2>&1
# -mindepth 1：别把备份根目录本身删了
find /srv/backup/skillmesh -mindepth 1 -maxdepth 1 -type d -mtime +30 -exec rm -rf {} +
```

二是用应用内置的定时器（`BackupScheduler`）。**默认关着**——
多副本部署时每个副本都备份一遍是白费力气，在一个实例上打开即可：

```bash
SM_BACKUP_DIR=/srv/backup/skillmesh   # 留空就不做备份
SM_BACKUP_SCHEDULE_ENABLED=true       # 打开定时备份
SM_BACKUP_INTERVAL_MS=3600000         # 间隔（默认 1 小时）
SM_BACKUP_INITIAL_DELAY_MS=600000     # 启动后多久第一次（默认 10 分钟）
SM_BACKUP_KEEP=24                     # 只留最近 24 份
```

内置定时器的每次备份落在 `<目录>/<时间戳>/` 里，超过保留份数的旧目录会删掉——
备份占的正是最要紧的那块盘，不清理迟早塞满。用 cron 时保留策略要自己写（上面那行 `find`）。

导出完立刻自检一遍——`verify()` 会逐个文件重算摘要与行数，对不上就报出来。**能导出不算数，能发现损坏才算**（自检的做法是：导出一份、验一遍、再故意改坏一个文件确认能报出来）。

导出按表流式写（`ResultSet` 边读边落 NDJSON，内存只占单行），大表也不会把进程撑爆。

### 恢复

恢复是把一份备份灌回库里的操作，**目标库得是空的**——恢复是往空库里灌，
目标表里还有数据会直接拒绝（覆盖还是报冲突，两样都不该悄悄发生）：

```bash
# 恢复到默认 schema（public）
bash infra/scripts/backup.sh restore /srv/backup/skillmesh/2026-10-30T03-00-00Z

# 恢复到别的 schema
bash infra/scripts/backup.sh restore /srv/backup/skillmesh/2026-10-30T03-00-00Z restored
```

要点：

- **先校验再恢复**：备份自己没坏（逐文件重算摘要与行数）才动手。
  校验不过直接拒绝——恢复出一份坏数据比不恢复更糟。
- **按外键顺序插**：父表先于子表。唯一被延后检查的约束
  （`skills.latest_version` → `skill_versions`）不参与排序，它留到提交时才查。
- **按列的类型转**：导出的值都是 JSON 里的字符串，插回去要转成 uuid、timestamptz、
  jsonb、text[] 这些列认得的形态，SQL 里用显式转型（`?::uuid`），不靠驱动猜。
- **序列要拨**：自增序列拨到表里最大的那条之后，否则恢复完再插新行会撞上已有的 id。
- **对象也一起放回**：制品按内容摘要寻址，重放一次是同内容覆盖。
  只恢复数据库（不想碰桶）时用 `BackupRestoreService.restoreDatabase`。
- **也绕开 Flyway**：迁移历史对不上时应用根本起不来，
  那恰恰是最需要备份、也最需要恢复的时候。

恢复用完先对账：`select count(*) from skills;` 之类核一遍行数，
再让一个真实用户登录、装一个 Skill 走通一遍。

## 看请求日志

每个请求都会记一行：方法、路径、状态、耗时、request_id。慢请求（超过 1 秒）单独记 warn。

```text
INFO  GET /api/v1/skills -> 200 （12ms）request_id=req_a1b2c3
WARN  POST /api/v1/uploads/xx/complete -> 201 （2340ms）request_id=req_d4e5f6
```

**request_id 也放在响应头 `X-Request-Id` 里**——客户端报障时把这个号给出来，
服务端能直接定位到那一次请求。客户端自己传 `X-Request-Id` 请求头就用他的。

审计流水（谁发布、谁审核、谁下载，见审计表）与请求日志是两回事：
请求日志记「这个接口调了多久」，审计记「谁做了什么动作」。

## 上传被代理挡下来（HTTP 413）

`skillmesh sync` 报「上传制品失败（HTTP 413）」，响应体还是一段 HTML——
这是**反向代理挡住的**：请求没到服务端，服务端的请求日志里也不会有这一次。

nginx 的 `client_max_body_size` 默认只有 **1m**，而 Skill 包稍微大一点就撞线
（几 MB 的技能目录压成 zip 就够）。仓库里的 `apps/web/nginx.conf` 与
`apps/web/nginx-tls.conf` 已经把 `/api/` 下的上限设成 64m，但**生产环境前面
那台自己装的 nginx 是另一份配置**，要自己改：

```nginx
location /api/ {
    client_max_body_size 64m;
    proxy_pass http://api:8080;
}
```

改完 `nginx -t && nginx -s reload`（compose 里是 `docker compose restart web`）。

上限要盖住服务端的制品上限 `SM_ARTIFACT_MAX_BYTES`（默认 50 MB）：
**调大服务端上限时这里要一起调**。反过来的顺序也行不通——
代理先拒的话，报的还是代理那句没头没尾的 413，而不是服务端给出的具体原因。

代理放行之后，服务端还有自己的闸门（`SM_ARTIFACT_MAX_BYTES`、
`SM_SCAN_MAX_FILE_BYTES` 等），那时报的错才是人话。

## 清理桶里的孤儿对象

对象存储里可能留着**没人引用的对象**：桶里有、`artifacts` 表里没有对应的 `storage_key`。
内容寻址之后不会再产生新的（同一份内容只写一次），但历史遗留的那批还在占地方。

```bash
# 只看清单，不删（删桶里的东西不可逆，先看清楚）
java -jar apps/api/target/skillmesh-api.jar --skillmesh.maintenance.purge-orphans=true

# 确认过再真删
java -jar apps/api/target/skillmesh-api.jar --skillmesh.maintenance.purge-orphans=delete
```

临时对象（`tmp/`、`sync-staging/`）不在清理范围内——它们由生命周期规则管，
删它们会打断正在传的上传。

有**一天宽限期**：比这还新的对象一律不动。发布流程里「对象写进桶」到
「`artifacts` 行提交」之间有个窗口，那一刻对象确实还没人引用——
没有宽限期就会把正在发布的内容删掉，版本随后指向一个不存在的对象。

## 用户与身份

账号分两处，别混：**身份**（怎么登录进来）与**权限**（组织、团队、角色）。
服务端自带账号体系，外部 IdP 是可选的一条旁路。

### 内置账号：服务端自己管用户名与密码

| 接口 | 用途 | 需要登录 |
| --- | --- | --- |
| `POST /api/v1/auth/register` | 注册（用户名唯一，不区分大小写） | 否 |
| `POST /api/v1/auth/login` | 用户名 + 密码换令牌 | 否 |
| `POST /api/v1/auth/refresh` | 刷新令牌换新令牌 | 否（凭刷新令牌） |

密码用 BCrypt 存储；登录成功签一对自签令牌（HS256），刷新令牌带 `typ` 标记，不能当访问令牌用。

| 环境变量 | 作用 | 默认值 |
| --- | --- | --- |
| `SM_JWT_SECRET` | 令牌的签名密钥。**生产必须固定**：不配就是每次启动随机生成，重启后所有人被登出 | 随机 |
| `SM_ALLOW_REGISTER` | 能不能自助注册。关掉只有管理员能建号 | `true` |
| `SM_ACCESS_TOKEN_MINUTES` | 访问令牌有效期（分钟） | `60` |
| `SM_REFRESH_TOKEN_DAYS` | 刷新令牌有效期（天） | `30` |

**第一个注册出来的内置账号是管理员**（`role=admin`），其余是普通账号。走外部 IdP 登录的老账号不占这个位置。

网页端与 CLI 都走这条路：网页登录页填用户名和密码；CLI `skillmesh login <服务端> --username <用户名>`，不给 `--password` 就在终端无回显输入。

### 管理员建号

自助注册关掉后，账号只能由管理员建。网页控制台侧栏的「账号」页就是干这个的：
管理员登录后能看到账号列表、建号、禁用与启用。

接口层面三个口子都要站点管理员（`users.role='admin'`）才放行：

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/users` | 账号列表（不含密码哈希） |
| `POST /api/v1/users` | 建号：`{"username","password","display_name","email"}`，新账号是普通用户 |
| `PATCH /api/v1/users/{id}/status` | 禁用或启用账号：`{"status":"disabled"}`。禁用后登不进来，账号与数据都留着 |

```bash
curl -X POST http://127.0.0.1:8080/api/v1/users \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"换成强口令","display_name":"爱丽丝"}'
```

CLI 不提供注册命令——账号统一由管理员建，建好后拿用户名密码去 `skillmesh login`。

### 管理员密码忘了（救急通道）

系统里**没有**改自己密码的接口：管理员能给别的账号建号、禁用，但改不了密码。
管理员密码一丢就没人能进后台，只能直接改库。仓库里备了一个离线工具：

```bash
bash infra/scripts/reset-password.sh list                       # 看有哪些内置账号
bash infra/scripts/reset-password.sh reset <用户名>              # 交互输入新密码
bash infra/scripts/reset-password.sh reset <用户名> --generate   # 随机生成，写到本地文件
bash infra/scripts/reset-password.sh reset <用户名> --enable     # 顺便把 disabled 的账号启用
```

- `--generate` 生成 20 位随机口令，写到 `~/.skillmesh-data/admin-password.txt`（只写这一次，用完删掉）。
- 不带 `--generate` 就在终端无回显输入；8～72 位，72 是 BCrypt 的硬上限。
- 工具不启动应用（密码忘了就登不进去，应用起不来的时候恰恰最需要它），只借 Spring 把数据源配好，不跑 Flyway、不跑 JPA 校验、不开端口。凭据从根目录 `.env` 读。
- **它改的是 `.env` 里 `SM_DB_URL` 指的那个库**——改哪个库，登录的就是哪个库。改完密码还是登不进去，先确认跑着的服务连的是不是同一个库（服务是在 `.env` 切换之前启动的，就会连着旧库）。

手工改库也行，记两条：哈希是 BCrypt（强度 10，密码 8～72 位），`users.role='admin'` 才算管理员。

> `.env` 里的 `SM_LOCAL_ADMIN_USERNAME` / `SM_LOCAL_ADMIN_PASSWORD` / `SM_LOCAL_ADMIN_HASH` 是**废配置，没有代码读它们**——改了不会生效，别拿它当重置途径。

### 外部 IdP（可选）

要接企业 SSO 时才配：网页端登录页会多出「用团队账号登录」按钮，CLI 不带 `--username` 就走授权码 + PKCE。

| 环境变量 | 作用 | 默认值 |
| --- | --- | --- |
| `SM_OIDC_ISSUER` | 外部 IdP 的 issuer。留空就只走内置账号 | 空 |
| `SM_OIDC_CLIENT_ID` | 网页端与 CLI 用的 client id | `skillmesh-cli` |
| `SM_MINIO_TEMP_EXPIRE_DAYS` | 上传临时对象几天后由对象存储自动清掉 | `1` |

issuer 与 client_id 由服务端经 `GET /api/v1/config/public` 交给前端，换 IdP 不用重新打包前端。

IdP 登录的用户第一次调 `GET /api/v1/me` 时自动建档。

### 权限侧：组织、团队与邀请

账号有了之后，权限靠组织与团队来管：

| 操作 | 谁来做 |
| --- | --- |
| 建组织、组建团队 | 用户自己（`POST /api/v1/organizations`、`/teams`） |
| 邀请成员进组织/团队 | 组织的 owner/admin（`POST /api/v1/organizations/{id}/invitations`） |
| 改成员角色 | 组织的 owner/admin（`PATCH /organizations/{id}/members/{userId}`） |
| **禁用/启用成员账号** | 组织的 owner/admin，同一个端点带 `{"status": "disabled"}`。禁用**立刻生效**——被禁用的账号令牌马上失效，所有请求被拒 |

账号状态存在 `users.status`（`active` / `disabled` / `pending`）。禁用的两条硬规则：**不能禁用自己的账号**，**不能禁用组织 owner**（owner 是组织的最后一道保险，禁掉他就没人能任命下一个了）。

> 账号从哪来取决于登录方式：内置账号是注册时建的，IdP 账号是第一次调 `/me` 时自动建档的。

### 上生产前必须处理

| 项 | 为什么 |
| --- | --- |
| 管理员的初始密码 | 第一个注册出来的账号就是管理员。注册完立刻改成强口令，或关掉自助注册（`SM_ALLOW_REGISTER=false`）由管理员在网页「账号」页建号 |
| `SM_JWT_SECRET` | 令牌的签名密钥。不配就是每次启动随机生成，重启后所有人被登出；泄露了则谁都能伪造令牌 |
| **HTTPS** | 设计文档 §14 要求「服务端使用 HTTPS；内部网络也不应依赖明文传输敏感凭据」。仓库里的 nginx 默认只 `listen 80`——上生产要么给 nginx 配证书（见下节「上 HTTPS」），要么在前面另放一个终止 TLS 的反向代理 |
| `SM_SIGNING_*`（三个） | 制品签名密钥。不配就不签名，客户端验签时只说「未验证来源」——用户分不清「没配」和「配了但坏了」 |
| 制品与扫描的限额 | `SM_ARTIFACT_MAX_BYTES` 等按环境调（磁盘小的地方调紧），别拿默认值硬扛 |
| 代理的请求体上限 | nginx 的 `client_max_body_size` 默认只有 1m，比服务端的制品上限小得多。不改的话上传一律 413，请求还到不了服务端（见「上传被代理挡下来」） |
| 批量同步撞限流 | `SM_RATE_LIMIT_WRITE` 默认 300 次/分钟；单机自用可直接设 `0` 关闭写限流，客户端也会按 `Retry-After` 退避 |
| 定期备份 | 用 cron 调 `infra/scripts/backup.sh`（见上），或在单个实例上开 `SM_BACKUP_SCHEDULE_ENABLED`；两种都要确认保留期策略有人管——备份目录会一直涨 |
| 恢复流程没人走过 | 备份能导出不等于能恢复。换台机器（或空 schema）真恢复一次，对完行数再让一个用户装一个 Skill——恢复路径要走过才算数 |

## 上 HTTPS

设计文档 §14 要求服务端用 HTTPS。证书要运维配合（域名、签发、续期、挂载），
所以代码只把路铺好：`apps/web/nginx-tls.conf` 是配好证书路径的 443 配置，
**默认不挂载**——镜像里没有证书，nginx 启动会因为找不到证书直接失败。

签发、续期、查有效期都走 `infra/scripts/tls-cert.sh`（certbot 的 webroot 模式）：

```bash
# 签（域名要已经解析到这台机器，80 端口对外通着）
bash infra/scripts/tls-cert.sh issue -d skills.example.com -m ops@example.com

# 续（certbot 只在快到期时才真续，续完自动 reload nginx）
bash infra/scripts/tls-cert.sh renew

# 看还有多久到期
bash infra/scripts/tls-cert.sh check -d skills.example.com
```

三步：

**1. 域名解析**：把域名指到这台机器的公网 IP。

**2. 签证书**：跑上面那条 `issue`（等价于
`certbot certonly --webroot -w ./infra/acme -d <域名>`）。
签之前要把 compose 里 `infra/acme` 挂进 web 服务的那行取消注释——
HTTP-01 校验要走 80 端口到这个目录。

**3. 挂上去**：改 `docker-compose.yml` 的 `web` 服务，把下面几行取消注释、
域名换成真的（`issue` 跑完会把这段直接打出来）：

```yaml
ports:
  - "127.0.0.1:8443:443"
volumes:
  - ./apps/web/nginx-tls.conf:/etc/nginx/conf.d/tls.conf:ro
  - /etc/letsencrypt/live/<域名>:/etc/nginx/certs:ro
  - ./infra/acme:/var/www/certbot:ro
```

然后 `docker compose up -d web`。

**续期**：脚本已经把「续完 reload nginx」挂成 certbot 的部署钩子，
所以 `renew` 完新证书就生效了。certbot 自己的定时任务（`certbot renew.timer`）
也可以留着，它会调同样的钩子。

**明文 80 端口**默认留着（证书续期与健康检查要用）。不想让明文直连应用，
就取消 `nginx-tls.conf` 末尾那个 80 端口 server 块的注释，80 会跳到 443。

**API 那边不用改**：compose 里 API 只映射到宿主机 `127.0.0.1:8080`，外部碰不到；
nginx 在 compose 内网里直连 `api:8080`。API 认 `X-Forwarded-For` 与
`X-Forwarded-Proto`（`server.forward-headers-strategy=framework`），
所以审计记的是真实来源 IP，限流也按真实 IP 分桶——不然所有请求都算在代理头上，
全站共用一个额度。

**代理必须覆盖 `X-Forwarded-For`，不能追加**。仓库里的 nginx 配的是
`proxy_set_header X-Forwarded-For $remote_addr`（覆盖）。
用追加的 `$proxy_add_x_forwarded_for` 会有个洞：客户端自己带一个
`X-Forwarded-For: 1.2.3.4`，追加后它排在最前面，而后端取的是第一个——
审计记的 IP 是客户端说了算的，限流的额度也能靠换 IP 绕过。
多一层代理（CDN 之类）时同理：让每一层都覆盖，别让客户端的值传下去。

**还要清掉 RFC 7239 的 `Forwarded` 头**。后端认它，而且优先级比 `X-Forwarded-For` 高：
客户端自己发一个 `Forwarded: for=1.2.3.4`，光覆盖 `X-Forwarded-For` 拦不住——
审计记的 IP 与限流分桶就由它说了算。仓库里的 nginx 配的是
`proxy_set_header Forwarded ""`（清空）。

`X-Forwarded-Host` 也要覆盖（`proxy_set_header X-Forwarded-Host $host`）：
主机名客户端能自己带，带了后端就会拿它拼绝对地址。

> 要把 API 直接放到公网前面（不走 nginx），就自己承担 TLS 终止，
> 并设 `SM_FORWARD_HEADERS_STRATEGY=none`：那个开关决定后端信不信
> `X-Forwarded-*` 这类头——信了，客户端就能伪造来源 IP 绕过限流。

## 制品签名密钥

服务端在制品定版时对清单摘要做 Ed25519 签名，客户端装之前会验签——**验签不通过就不装**。不配密钥就不签（空签名不会被误当成验过了），CLI 这时只说「未验证来源」。

```bash
openssl genpkey -algorithm ed25519 -out skillmesh-signing.pem
openssl pkey -in skillmesh-signing.pem -pubout -outform DER | tail -c 32 | base64 -w0   # 公钥
openssl pkcs8 -topk8 -nocrypt -in skillmesh-signing.pem -outform DER | base64 -w0          # 私钥
```

```bash
SM_SIGNING_PRIVATE_KEY=<私钥 base64>
SM_SIGNING_PUBLIC_KEY=<公钥 base64>
SM_SIGNING_KEY_ID=2026-10
```

客户端侧怎么把公钥钉成信任根，见 [CLI 使用手册](cli-使用手册.md#装之前看一眼来源与风险)。

## 受限网络下访问 GitHub

本机到 GitHub 的连通性是**分主机**的，不是简单的"能"或"不能"。2026-10-19 实测：

| 主机 / 端口 | 状态 | 备注 |
| --- | --- | --- |
| `github.com:443` | ❌ 不通 | `git clone https://github.com/...` 必然失败 |
| `github.com:22` | ✅ 通 | SSH 通道可用，缺的只是密钥 |
| `github.com:9418` | ❌ 不通 | git:// 协议 |
| `api.github.com` | ✅ 200 | REST API 可用 |
| `codeload.github.com` | ✅ 200 | 仓库归档 tarball 可用 |
| `raw.githubusercontent.com` | ❌ 不通 | 原始文件直取不可用 |
| `objects.githubusercontent.com` | ✅ 通 | release 资源 CDN |

结论：**SSH 和 API 两条路是通的，网页和 https clone 不通**。下面三条路径任选其一。

### 路径 A：配 git 代理（最省事）

代理客户端（Clash for Windows / v2rayN）启动后：

```powershell
# 全局生效
git config --global http.proxy  http://127.0.0.1:7890
git config --global https.proxy http://127.0.0.1:7890
```

想**只让 GitHub 走代理**，不影响其他流量（推荐）：

```powershell
git config --global http.https://github.com.proxy http://127.0.0.1:7890
```

撤销：

```powershell
git config --global --unset http.proxy
git config --global --unset https.proxy
git config --global --unset http.https://github.com.proxy
```

端口按你实际用的客户端：Clash for Windows 默认 **7890**（HTTP）/ 7891（SOCKS），v2rayN 常见 **10809**（HTTP）/ 10808（SOCKS）。`~/.m2/settings.xml` 里那两个 `active=false` 的代理条目指向 `127.0.0.1:7890` 和 `33210`，说明之前用的是 Clash。

配完直接用 https 形式的地址：

```powershell
cd D:\dev\MyProject\SkillMesh\apps\cli
.\skillmesh.exe source resolve https://github.com/phuryn/pm-skills
```

### 路径 B：SSH 密钥（一次配置，长期免代理）

好处是代理不开也能 clone。仓库里已备好 `~/.ssh/id_ed25519`（ed25519，无口令，注释 `skillmesh-dev`）——**私钥留在本机，权限 600，只把公钥注册到 GitHub**。

注册公钥需要一个带 `admin:public_key` 权限的 Personal Access Token。**建 PAT 本身要走 github.com 的网页，所以这一步仍然需要把代理开起来**——只有这一次。

**建 PAT**：

1. 代理开着的情况下访问 <https://github.com/settings/tokens>
2. 页面顶部点 **Generate new token** → **Generate new token (classic)**
3. **Note** 填 `skillmesh-dev`，**Expiration** 按需设（默认 30 天，到期后重注册）
4. 勾选权限里的 **`admin:public_key`**（描述是 "Full control of public keys"）——只需要这一个
5. 点 **Generate token**，**立刻复制** `ghp_...`（只显示这一次）

> 用 fine-grained token 也行：<https://github.com/settings/personal-access-tokens/new> → Permissions → Account permissions → **SSH public keys** → **Read and write**。

**注册公钥**（令牌只从环境变量读，不落盘、不进 shell 历史）。脚本是 bash 版，在 Git Bash 里执行：

```bash
cd D:\dev\MyProject\SkillMesh
export GITHUB_TOKEN=ghp_你的令牌
bash infra/scripts/register-github-ssh-key.sh
```

脚本会 POST 到 `api.github.com/user/keys`，然后列出账号当前的密钥列表。已注册过会提示 `already_exists` 而不是报错。

**验证**：

```powershell
ssh -T git@github.com
# 期望：Hi <你的用户名>! You've successfully authenticated, but GitHub does not provide shell access.
```

**用起来**——CLI 走 SSH 地址：

```powershell
cd D:\dev\MyProject\SkillMesh\apps\cli
.\skillmesh.exe source resolve git@github.com:phuryn/pm-skills
.\skillmesh.exe add git@github.com:phuryn/pm-skills.git --path skills/xxx --agent claude-code
```

`gitx.NormalizeURL` 已支持 `git@owner:repo.git` 形式（也支持 `ssh://`）。注意 SSH 地址**不能带 `https://` 前缀**，两种形式不能混写。

### 路径 C：codeload 归档（未实现）

`codeload.github.com` 是通的，所以理论上可以在 git clone 失败时回退到 `https://codeload.github.com/{owner}/{repo}/tar.gz/{ref}` 取快照。**这还没做**，而且会丢掉 commit 粒度（只能按 ref 取树，commit SHA 得另外从 API 拿），属于产品特性而非 bug 修复。

### 故障排查

| 报错 | 原因 | 处理 |
| --- | --- | --- |
| `Permission denied (publickey)` | 公钥没注册，或 ssh 没找到私钥 | `ssh -v -T git@github.com`，看有没有 `Will attempt key: ... id_ed25519` |
| 上面那行没有出现 | 私钥路径不对 | 确认在 `C:\Users\23929\.ssh\id_ed25519`；或 `ssh -i <路径>` 指定 |
| `Host key verification failed` | known_hosts 里没有 github.com | `ssh-keyscan github.com >> $env:USERPROFILE\.ssh\known_hosts` |
| `UNPROTECTED PRIVATE KEY FILE` | 私钥 ACL 对其他用户开放 | 见下方 ACL 收紧命令 |
| `Could not read from remote repository` + `Connection reset` | 走的是 https，443 不通 | 换 `git@github.com:owner/repo.git`，或配代理（路径 A） |
| `Repository not found`（明明存在） | 同上，https 走了不通的链路 | 同上 |
| API 返回 401 | PAT 无效或过期 | 重建 PAT |
| `docker compose` 起不来，API 报拉不到 issuer | 配了 `SM_OIDC_ISSUER` 但那个 IdP 不可达 | 服务端只在第一次解码外部令牌时才去解析 issuer，IdP 不可达只是那一次请求 401，服务照常起；不接 IdP 就把 `SM_OIDC_ISSUER` 留空 |
| API 返回 403 且提示缺 scope | PAT 没勾 `admin:public_key` | 重建 PAT，注意勾对权限 |
| API 返回 422 `already_exists` | 该公钥已注册 | 脚本会识别为正常情况，可直接继续 |

私钥 ACL 收紧（Windows OpenSSH 拒绝权限过开的私钥）：

```powershell
icacls "$env:USERPROFILE\.ssh\id_ed25519" /inheritance:r /grant:r "$env:USERNAME:(R)"
```

本机当前状态已经是对的（`SYSTEM` / `Administrators` / 本人，无 `Everyone` / `Users` 组），Git Bash 的 ssh 和 `C:\Windows\System32\OpenSSH\ssh.exe` 都正常认这把钥匙。

### 现状

本机已生成 `~/.ssh/id_ed25519`，**但公钥还没注册到 GitHub 账号**（注册需要 PAT，需要先开代理建 PAT）。所以目前 `git clone https://github.com/...` 仍然会失败，CLI 会给出带代理提示的错误（见 `gitx` 的网络失败处理）。
