# 团队治理与安全

组织、团队、角色、可见性、发布审核、安装登记、审计与制品签名。
只影响多个人一起用的情况；单人使用可以先看 [CLI 使用手册](cli-使用手册.md)。

## 团队与审核

```bash
skillmesh review submit  <skill-id> <version> --comment "初版"
skillmesh review approve <skill-id> <version> --comment "没问题"
skillmesh review reject  <skill-id> <version> --comment "第 3 节有危险命令"
```

个人与公开的 Skill 扫描通过即发布；**团队与组织可见的版本会停在待审核**（设计文档 §10.1），且**不能审自己发的版本**。审核结论写 `skill_reviews`，同时进审计流水。

可见性规则：public 谁都能看，private 只有属主，`organization` 要组织成员，`team` 要**该团队的成员或该组织的 owner/admin**——搜索也按这个过滤（不是查出来再在内存里筛）。

（`team` 为什么带上组织的 owner/admin：建团队时不写团队成员行，组织 owner 在该团队没有角色；若只认团队成员，他读不到、搜不到自己团队的东西，而他在审核队列里却能看见并批准它——「能批不能看」说不通。团队的普通成员看不到别的团队的 Skill。）

```bash
curl -X POST .../api/v1/organizations -d '{"slug":"acme","name":"Acme"}'
curl -X POST .../api/v1/organizations/<id>/teams -d '{"slug":"platform","name":"平台组"}'
curl -X POST .../api/v1/teams/<id>/members -d '{"user_id":"...","role":"reviewer"}'
```

## 角色分两层

角色是**两套**的：组织一套、团队一套，**各管各的事**。

| 层 | 角色（从高到低） |
| --- | --- |
| 组织角色 | owner / admin / publisher / reviewer / member / viewer |
| 团队角色 | admin / publisher / reviewer / member / viewer |

**团队没有 owner 这一档**——组织才有。给团队成员填 `owner` 服务端会 400，提示角色只能是 admin / publisher / reviewer / member / viewer 之一。组织里的 owner 也**不能通过邀请拿到**，只能由现任 owner 直接任命；邀请能授的只有 admin 及以下。

建组织的人自动是组织 owner。`GET /api/v1/me` 会列出你所在的组织和**组织**角色；团队角色在 `GET /api/v1/organizations/<id>/teams/<team-id>/members` 里看。

### 分层职责：看哪一层的角色

| 做什么 | 看哪一层的角色 | 门槛 |
| --- | --- | --- |
| 发布到组织/团队（`publish --org/--team`） | **组织角色** | publisher 及以上 |
| 提交审核（`review submit`） | **组织角色** | publisher 及以上 |
| 审核放行（`review approve`/`reject`） | **团队角色** | reviewer 及以上 |
| 审核队列里看得见哪些待审版本 | **团队角色** | reviewer 及以上 |
| 管成员、发邀请 | **组织角色** | owner / admin |
| 管某个团队的成员 | **组织角色**，或你在该团队里是 **admin** | 组织 owner / admin，或该团队 admin |
| **禁用/启用成员账号** | **组织角色** | owner / admin |

两处要留意：

- **审核这一侧先看团队角色**。团队范围的版本，你在那个团队里有成员行就用那个角色，**没有成员行才回落到组织角色**；组织范围的版本只有组织角色这一层。所以光有组织 reviewer 身份、但在这个团队里有个 `member` 的成员行，队列里反而看不到——得改的是**团队角色**。
- **发布这一侧只看组织角色**。`publish --org/--team` 的权限判在组织上，接受邀请写下的 `team_role=member` 不会遮住它。要往团队发东西，得让组织管理员把你的**组织角色**提到 publisher。

### 权限是怎么判的

服务端把「角色」和「权限」分开：角色是**你是谁**（上表那两套词表），权限是**你能做什么**（`Permission` 枚举，11 个权限点）。

| 权限点 | 谁有 |
| --- | --- |
| `ORG_INVITE` / `ORG_MANAGE_MEMBERS` / `ORG_MANAGE_TEAMS` | 组织 owner / admin |
| `ORG_GRANT_OWNER` / `ORG_REVOKE_OWNER` | 组织 owner（仅此一档） |
| `ORG_VIEW_MEMBERS` | 所有组织角色 |
| `TEAM_VIEW_MEMBERS` | 所有团队角色，以及所有组织角色 |
| `TEAM_MANAGE_MEMBERS` | 团队 admin，或组织 owner / admin |
| `SKILL_PUBLISH` / `GROUP_PUBLISH` | 组织 publisher 及以上；团队 publisher 及以上（仅集合） |
| `SKILL_REVIEW` | 组织 reviewer 及以上，或团队 reviewer 及以上 |

角色到权限的映射写在 `RolePermissions` 里（两张表：组织角色、团队角色），判定统一走 `AuthorizationService`——权限门槛不再散落在各个 Service 里手写角色名。

> 改权限时改 `RolePermissions` 的映射表，别去改各个 Service——散开的门槛加一档角色要改十几个地方，漏一处就是一条越权路径。
> 归属（属主才能改的东西：改 Skill、发新版本、撤回版本、改集合）是另一回事，不在角色权限体系里，由 `AuthorizationService.requireOwner` 单独判。

界面也吃同一份判定：`GET /api/v1/organizations/<id>/permissions` 给出当前用户在这个组织下的权限点，网页端据此决定按钮显隐——没有的权限点了也是 403，不如不显示。审核页更进一步：每条待审版本带 `can_decide` / `can_approve`（能不能驳回、能不能放行），由服务端算好给前端，前端不自己推规则。

## 禁用账号

`PATCH /api/v1/organizations/<id>/members/<user-id>` 带 `{"status": "disabled"}`——
组织 owner / admin 能禁用本组织的成员。**禁用立刻生效**：被禁用的账号令牌马上失效，所有请求被拒（403）。

两条硬规则：

- **不能禁用自己的账号**——不然就把自己的路堵死了。
- **不能禁用组织 owner**——owner 是组织的最后一道保险，禁掉他就没人能任命下一个了。要换 owner 先降级再禁用（得分两次请求）。

> 团队没有这一层：团队成员不涉及账号禁用，只有组织这一层管。

## 删掉的文件能找回来

一版比上一版少的文件不是消失了——它进**云端回收站**，回收期 30 天。

```bash
skillmesh recycle list              # 某个 Skill 里被删掉的文件
skillmesh recycle restore old.md    # 放回去，产出一个新版本
```

`GET /api/v1/skills/<id>/recycle` 列出，`POST /api/v1/skills/<id>/recycle/restore` 恢复
（请求体 `{"path": "old.md"}`）。
恢复走**正常发版流程**：扫描、审核那道闸一样要过——团队可见的 Skill 恢复回去照样要等人审。

> 本机的回收站是 `skillmesh trash`（卸载掉的 Skill），跟这个不是一回事。

## 审计

发布、撤回、制品下载、审核结论都写 `audit_events`（谁、什么时候、对哪个对象、结果、附带细节）。Skill 的生命周期也记：新建（`skill.created`）、改元数据（`skill.updated`，details 里带改了哪些字段）、删除与还原（`skill.archived` / `skill.restored`）。

```bash
curl -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8080/api/v1/skills/<skill-id>/audit
```

**客户端也会上报一部分**：同步上传（`sync.uploaded`）、拉回云端版本（`sync.downloaded`）、以及**云端删掉后本地那份跟着被移进回收站**（`sync.local_deleted`）——最后一类只有客户端看得见，服务端那边只有版本记录。能上报的动作是白名单，不在名单里的一律 400；上报时还要确认上报者跟这个 Skill 真有关系（属主、组织或团队成员、装过它），否则谁都能往别人的流水里塞条目。完整动作清单见[详细设计 §2.2.1](详细设计.md)。

**两个查询端点当前只查得到 Skill 维度的事件**——`GET /api/v1/skills/<skill-id>/audit` 与 `GET /api/v1/audit-events` 都按 `target_type='skill'` 过滤。治理类事件（`invitation.*`、`organization.*`、`team.*`、`*.membership.*`）写进了 `audit_events`，但因为目标类型不是 skill，**目前一条也查不出来**（`device.revoke` 同理）；`request_id` 这一列也始终是空的（服务端从不写它）。要查治理流水需要改查询端点，那是后续的事。

审计写入失败不会回滚业务动作——事情已经发生了，记不上是另一回事，会在日志里留一条失败记录。

**本机还有一份操作日志**：CLI 把这台机器上的动作写进 `<缓存目录>/operations.log`（一行一条 JSON），服务端看不来的细节靠它——云端删除传到本地后删的是哪个目录、装到了哪里、哪一步失败了。`skillmesh logs` 看，`skillmesh logs --skill <名字>` 只看某个 Skill。日志里写路径前会先脱敏：家目录换成 `~`，家目录外的绝对路径只留末两段——这份日志是要被用户贴到 issue 里的，家目录布局和令牌不该跟着出去。
