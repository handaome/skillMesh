# 团队治理与安全

组织、团队、角色、可见性、发布审核、安装登记、审计与制品签名。
只影响多个人一起用的情况；单人使用可以先看 [CLI 使用手册](cli-使用手册.md)。

## 团队与审核

```bash
skillmesh review submit  <skill-id> <version> --comment "初版"
skillmesh review approve <skill-id> <version> --comment "没问题"
skillmesh review reject  <skill-id> <version> --comment "第 3 节有危险命令"
```

个人与公开的 Skill 扫描通过即发布；**团队与组织可见的版本会停在待审核**（设计文档 §10.1），且**不能审自己发的版本**。审核结论写 `skill_reviews`，同时进审计流水。

可见性规则：public 谁都能看，private 只有属主，`organization` 要组织成员，`team` 要**该团队的成员或该组织的 owner/admin**——搜索也按这个过滤（不是查出来再在内存里筛）。

（`team` 为什么带上组织的 owner/admin：建团队时不写团队成员行，组织 owner 在该团队没有角色；若只认团队成员，他读不到、搜不到自己团队的东西，而他在审核队列里却能看见并批准它——「能批不能看」说不通。团队的普通成员看不到别的团队的 Skill。）

```bash
curl -X POST .../api/v1/organizations -d '{"slug":"acme","name":"Acme"}'
curl -X POST .../api/v1/organizations/<id>/teams -d '{"slug":"platform","name":"平台组"}'
curl -X POST .../api/v1/teams/<id>/members -d '{"user_id":"...","role":"reviewer"}'
```

## 角色分两层

角色是**两套**的：组织一套、团队一套，**各管各的事**。

| 层 | 角色（从高到低） |
| --- | --- |
| 组织角色 | owner / admin / publisher / reviewer / member / viewer |
| 团队角色 | admin / publisher / reviewer / member / viewer |

**团队没有 owner 这一档**——组织才有。给团队成员填 `owner` 服务端会 400，提示角色只能是 admin / publisher / reviewer / member / viewer 之一。组织里的 owner 也**不能通过邀请拿到**，只能由现任 owner 直接任命；邀请能授的只有 admin 及以下。

建组织的人自动是组织 owner。`GET /api/v1/me` 会列出你所在的组织和**组织**角色；团队角色在 `GET /api/v1/organizations/<id>/teams/<team-id>/members` 里看。

### 分层职责：看哪一层的角色

| 做什么 | 看哪一层的角色 | 门槛 |
| --- | --- | --- |
| 发布到组织/团队（`publish --org/--team`） | **组织角色** | publisher 及以上 |
| 提交审核（`review submit`） | **组织角色** | publisher 及以上 |
| 审核放行（`review approve`/`reject`） | **团队角色** | reviewer 及以上 |
| 审核队列里看得见哪些待审版本 | **团队角色** | reviewer 及以上 |
| 管成员、发邀请 | **组织角色** | owner / admin |
| 管某个团队的成员 | **组织角色**，或你在该团队里是 **admin** | 组织 owner / admin，或该团队 admin |

两处要留意：

- **审核这一侧先看团队角色**。团队范围的版本，你在那个团队里有成员行就用那个角色，**没有成员行才回落到组织角色**；组织范围的版本只有组织角色这一层。所以光有组织 reviewer 身份、但在这个团队里有个 `member` 的成员行，队列里反而看不到——得改的是**团队角色**。
- **发布这一侧只看组织角色**。`publish --org/--team` 的权限判在组织上，接受邀请写下的 `team_role=member` 不会遮住它。要往团队发东西，得让组织管理员把你的**组织角色**提到 publisher。

## 审计

发布、撤回、制品下载、审核结论都写 `audit_events`（谁、什么时候、对哪个对象、结果、附带细节）。

```bash
curl -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8080/api/v1/skills/<skill-id>/audit
```

**两个查询端点当前只查得到 Skill 维度的事件**——`GET /api/v1/skills/<skill-id>/audit` 与 `GET /api/v1/audit-events` 都按 `target_type='skill'` 过滤。本分支新增的治理类事件（`invitation.*`、`organization.*`、`team.*`、`*.membership.*`）写进了 `audit_events`，但因为目标类型不是 skill，**目前一条也查不出来**（`device.revoke` 同理）；`request_id` 这一列也始终是空的（服务端从不写它）。要查治理流水需要改查询端点，那是后续的事。

审计写入失败不会回滚业务动作——事情已经发生了，记不上是另一回事，会在日志里留一条失败记录。
