### P0-1　`isBinaryContent` —— 逐字重复两份，零行为风险

**问题一句话**：同一个「是不是二进制文件」的判断，在 `cmd` 包和 `skillscan` 包各写了一份，逐字相同。

**证据**

```text
apps/cli/internal/cmd/diff.go:126
func isBinaryContent(data []byte) bool {
	head := data
	if len(head) > 8192 {
		head = head[:8192]
	}
	return bytes.IndexByte(head, 0) >= 0
}
```

```text
apps/cli/internal/skillscan/risks.go:179
func isBinaryContent(data []byte) bool {
	head := data
	if len(head) > 8192 {
		head = head[:8192]
	}
	return bytes.IndexByte(head, 0) >= 0
}
```

**为什么算重复**：两个函数体逐字一致（同 8192 字节窗口、同 NUL 字节判定）。任何一边改了窗口长度或判定规则，另一边就悄悄漂移——而这两个函数分属「差异展示」和「风险扫描」两条链路，漂移后会出现「扫描说不是二进制、差异面板说是二进制」的自相矛盾。

**提取方案**

- 目标类：`apps/cli/internal/skillscan/risks.go`（原地导出，不新建包）
- 方法签名：`func IsBinaryContent(data []byte) bool`
- 参数：`data []byte` —— 待判定的字节内容
- 返回值：`bool` —— 前 8192 字节内含 NUL 即视为二进制
- 调用方改造：`apps/cli/internal/cmd/diff.go` 删除本地实现，改调 `skillscan.IsBinaryContent(...)`。
  **前置条件已满足**：`cmd/diff.go` 第 11 行已经 `import "github.com/handaome/skillmesh/apps/cli/internal/skillscan"`，无需新增依赖。

**影响面**

- `apps/cli/internal/skillscan/risks.go`：函数改名为导出
- `apps/cli/internal/cmd/diff.go`：删除本地函数 + 改调用点（1 处）
- 无其他文件引用这两个私有函数（已做全仓未引用符号扫描确认）

**预期收益**：消除一处必然漂移点；净减约 7 行；改动面 2 个文件，可单测/单跑 `skillmesh diff` 验证。

### P1-1　相对路径安全校验 —— 同一道安全闸散在 3 处

**问题一句话**：「这个相对路径能不能写进 zip / 能不能存进对象存储」这条安全判断，在服务端 3 个包里各写一遍，规则还略有出入。

**证据**

```text
apps/api/src/main/java/com/skillmesh/api/scan/ArtifactScanner.java:145
                if (path.startsWith("/") || path.contains("..")) {
                    findings.add(new ScanResult.Finding(path, 0, RULE_PATH_TRAVERSAL,
                        "制品里出现越界路径，不该发到云端"));
                    continue;
                }
```

```text
apps/api/src/main/java/com/skillmesh/api/sync/SyncUploadService.java:372
    /** 同步路径不能逃出变更集目录。 */
    private void requireSafePath(String path) {
        if (path == null || path.isBlank() || path.startsWith("/") || path.contains("..")) {
            throw new ApiException(400, ErrorCodes.VALIDATION_FAILED,
                "相对路径不合法：" + path);
        }
    }
```

```text
apps/api/src/main/java/com/skillmesh/api/version/VersionEditService.java:266
    private String normalizePath(String raw) {
        String path = raw == null ? "" : raw.trim().replace('\\', '/');
        while (path.startsWith("/")) {
            path = path.substring(1);
        }
        if (path.isBlank()) {
            throw new ApiException(400, ErrorCodes.VALIDATION_FAILED, "文件路径不能为空");
        }
        if (path.contains("..")) {
            throw new ApiException(400, ErrorCodes.VALIDATION_FAILED,
                "文件路径不能包含 ..");
        }
        return path;
    }
```

**为什么算重复**：三处都在回答同一个问题——「这个路径会不会跑出目标目录」，但判定与处置各不相同：

| 位置 | 前导 `/` | `..` | 空路径 | 处置方式 |
| --- | --- | --- | --- | --- |
| `ArtifactScanner` | 记 finding | 记 finding | 不判 | 不抛异常，继续扫下一个 entry |
| `SyncUploadService` | 拒绝 | 拒绝 | 拒绝 | 抛 `ApiException(400)` |
| `VersionEditService` | **剥掉**（归一化） | 拒绝 | 拒绝 | 抛 `ApiException(400)` |

规则一旦漂移，就是安全边界漂移——`VersionEditService` 之所以剥掉前导 `/` 而不是拒绝，是因为它要写进 zip 的 entry 名（`zip-slip`）；`SyncUploadService` 之所以拒绝，是因为变更集路径是要回写对象存储 key 的。这两者的**意图不同是对的**，但**「含 `..` 即拒绝」这条底线规则是同一条**，应当共用一个判定谓词，处置差异留在调用方。

**提取方案**

- 目标类：`apps/api/src/main/java/com/skillmesh/api/common/SafePath.java`（新建，`api/common` 已是公共工具包）
- 方法签名：
  - `public static boolean containsTraversal(String path)` —— 参数：待判定的相对路径（可为 null）；返回值：路径是否含 `..` 段或绝对路径前缀（即「会逃出目标目录」）
  - `public static String normalize(String raw)` —— 参数：原始路径（null 安全）；返回值：归一化后的相对路径（统一反斜杠、剥前导 `/`）；**是否拒绝由调用方决定**
- 参数/返回值约定：`normalize` 只做「规整」不做「裁决」，抛不抛 `ApiException` 由调用方按各自场景决定（`ArtifactScanner` 仍然只记 finding 不抛）
- 调用方改造：
  - `ArtifactScanner.java:145` → `if (SafePath.containsTraversal(path))`
  - `SyncUploadService.java:373` → `if (path == null || path.isBlank() || SafePath.containsTraversal(path))`
  - `VersionEditService.java:274` → `if (SafePath.containsTraversal(path))`，`normalizePath` 内部改调 `SafePath.normalize(raw)`

**影响面**

- 新增：`apps/api/src/main/java/com/skillmesh/api/common/SafePath.java`
- 修改：`ArtifactScanner.java`、`SyncUploadService.java`、`VersionEditService.java`（各 1–3 行 + import）

**预期收益**：把「路径不能逃出目标目录」这条底线规则收敛成单一事实来源；同时给后续新增入口（上传、编辑、扫描）一个现成的检查入口——这是最容易在加功能时被漏掉的地方。

**回归要点**：上传（`SyncUploadService`）、编辑（`VersionEditService`）、扫描（`ArtifactScanner`）三条链路各跑一次。

## 六、不建议动（复核认为过度抽象、抽了反而更糟的地方）

1. **`apps/api/src/main/java/com/skillmesh/api/org/Roles.java` 里的「正则与集合双份写法」**——`INVITABLE_ORG_ROLE_PATTERN` / `TEAM_ROLE_PATTERN` 是 `@Pattern` 注解用的编译期常量，`ORG_ROLES` / `TEAM_ROLES` 是运行期集合，看起来重复，但 `@Pattern` 只接受编译期常量，运行时拼不出常量表达式。该类已用静态块主动盯着两边不漂移（不一致直接抛异常），这是「有意重复 + 有防漂移机制」，抽掉反而更脆。
2. **`apps/api/src/main/java/com/skillmesh/api/skill/VisibleSkills.java` 里的原生 SQL 片段与 `SkillService.canView` 的 Java 判定**——同一套可见性口径写了两份（SQL 片段 vs Java 逻辑），看似该合并，但一个在数据库侧、一个在应用侧，且 SQL 片段必须是编译期常量字符串。类注释已写明「两处必须一起改」。强行统一只能靠生成 SQL，风险高于收益。
3. **`apps/api/.../artifact/ZipManifest.java` 的 `java.util.zip` 与 `ZipRewriter` 的 `commons-compress`**——两套 zip 库并存看似该统一，但 `ZipRewriter` 明确需要 `commons-compress` 的 unix 权限位支持（`java.util.zip` 没有），而 `ZipManifest` 的读取路径刻意只用 JDK 实现。两者的需求不同，不是重复。
4. **`apps/web/src/utils/format.ts` 目前只放一个 `formatDateTime`**——不要为了「看起来像个工具模块」而提前把大大小小几十个格式化函数塞进去。当前只有一个函数、单独成文件已经够清晰；等真的出现第二个、第三个同类函数再聚合。
5. **不要为 Go 的 `tabwriter` 场景造一个通用「表格渲染框架」**——P0-2 只抽一个 `newTable()` 就够了。再往上抽象（列定义、排序、边框、颜色）在这个 CLI 里没有第二个使用场景，属于典型的 YAGNI。
6. **不要把 Java 各 Service 里的 `record` DTO 合并成一个大而全的响应模型**——`VersionFilesResponse`、`SkillPage`、`InvitationSummary` 等虽然字段有交集，但各接口的契约裁剪不同，合并后会把「对外暴露哪些字段」的决定权从各接口收走。
7. **不要把 `apps/cli/internal/cmd` 下 30 个命令文件的公共流程（`install` / `update` / `add`）强行合成一个框架**——三者虽都涉及「装到 Agent 目录」，但安装、更新、冲突解决的失败语义与回滚策略各不相同（`install` 要原子切换、`update` 要备份旧版本、`conflict` 要保留双方），合成后的分支复杂度远超收益。
