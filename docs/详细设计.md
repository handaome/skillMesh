# SkillMesh 数据库 SQL、接口规范与 CLI 命令详细设计

> 文档版本：V1.0  
> 日期：2026-10-19  
> 产品名称：SkillMesh  
> 文档类型：研发接口与数据设计基线  
> 适用范围：后端、CLI/Daemon、Web 前端、测试、运维与安全评审

本文在《SkillMesh：Agent Skill 协作与分发平台最终设计文档》的基础上，将核心设计落实为可用于项目初始化和接口联调的数据库 DDL、接口清单和 CLI 行为规范。示例域名、OIDC Issuer、对象存储地址及部分策略参数是部署占位值，上线时由环境配置提供。

## 0. 设计约束与约定

### 0.1 必须遵守的规则

1. **Skill 内容与安装实例分离**：Skill 的云端逻辑实体、每个不可变版本、Git 来源、本地安装实例分别建模。
2. **发布版本不可变**：已发布版本的内容、摘要、制品地址不可原位更换；有修改必须创建新版本。
3. **本地同步默认私有**：本地目录同步至个人空间不等同于团队发布；团队共享需要单独授权或审核。
4. **来源可追溯**：Git 安装记录仓库、子目录、ref、实际解析 commit 和内容摘要；不把凭据写入 URL、日志或 Skill 文件。
5. **安全后安装**：下载先进入临时目录，完成路径校验、大小限制、摘要验证和策略扫描后，才替换 Agent 目录中的当前版本。
6. **冲突不静默覆盖**：双向同步以共同基线比较；同一文件两端都变化时，优先三方合并，无法合并则保留冲突副本并暂停该 Skill 的自动覆盖。
7. **API 授权由服务端决定**：客户端传入的组织 ID、团队 ID、Skill ID 均不代表授权。每次读取、下载、发布、审批都必须服务端鉴权。
8. **凭据不进入制品**：Git 凭据引用只指向本机凭据管理器或服务端受控 Secret 引用；不得将长期令牌写入数据库普通字段。

### 0.2 命名规范

- API 前缀：`/api/v1`。
- JSON 字段：`snake_case`。
- 数据库表与字段：`snake_case`；主键使用 UUID。
- 时间字段统一使用 `timestamptz`，存储 UTC。
- 版本摘要使用 SHA-256 十六进制小写字符串。
- 标识符 ID 与展示用 `slug` 分离。`slug` 不作为安全授权凭据。
- API 错误统一返回 `application/problem+json` 风格的 JSON 错误对象。
- 列表接口统一支持 `limit`、`cursor`；不使用会因插入而漂移的深分页 offset 作为主要分页方式。

# 第一部分：PostgreSQL 数据库设计

## 1.1 数据库选型和迁移约束

- 数据库：PostgreSQL 15 或更高版本。
- UUID 默认使用 PostgreSQL `gen_random_uuid()`；需要 `pgcrypto` 扩展。
- DDL 通过 Flyway 或 Liquibase 管理，生产环境禁止人工直接修改表结构。
- 应用数据库账号不应拥有 `SUPERUSER`；扩展由数据库管理员预先安装。
- 审计数据按月分区（`audit_events` 按 `occurred_at` 做 RANGE 分区），保留期过了整月分区直接 DROP；保留多少个月由 `skillmesh.audit.retention-months` 定（默认 12）。
- 对象存储中的 Skill 制品与数据库事务无法形成传统分布式事务，上传采用“先写临时对象、校验成功、数据库提交、异步清理孤儿对象”的流程。

## 1.2 完整初始化 DDL

初始 schema 在 `apps/api/src/main/resources/db/migrations/V1__init.sql`
（20 张表，Flyway 负责建库），之后的改动走增量迁移。当前迁移链共 13 条：
V1–V6、V11–V17。V7–V10 是旧链用过的号，已被跳过，别往里填——下一个可用版本号是 V18
（`infra/scripts/check-migrations.sh` 会检查这件事）。表总数 22：V4 加了 `skill_groups`，
V17 加了 `idempotency_keys`（幂等键，见 §2.1）。

本文档不抄 DDL 副本，**schema 以迁移脚本为准**；表间关系见 [数据库 ER 图](数据库ER图.md)，§1.3 起是这份 DDL 背后的设计取舍。

### 1.3 DDL 落地说明

1. `skills.latest_version` 是查询优化字段，必须由发布事务统一更新；不能允许客户端直接指定任意值。发布事务应验证对应 `skill_versions.status = 'published'`。
2. SQL 层无法仅靠普通 `CHECK` 约束实现跨表的“发布后不可修改”规则。服务层必须禁止修改已发布版本的 `artifact_id`、`version`、`source_commit`、`manifest_json`；生产环境可增加数据库触发器作为纵深防护。
3. `repository_url` 的简单约束只用于阻止常见带账号密码 URL，并不能替代 URL 规范化和 SSRF 防护。服务层仍需禁止危险协议、回环/链路本地地址和不允许的重定向。
4. `skills` 的唯一索引允许个人空间与组织空间使用同名 `slug`。服务层应统一 slug 规则，例如小写字母、数字、连字符，长度 2–64。
5. `installations` 的 `target_path` 是本机路径信息，仅用户本人及必要的平台诊断功能可访问，不应暴露给团队市场公开查询。
6. 私有云端草稿可以使用 `skills.visibility='private'` 和 `skill_versions.status='draft'` 表示；正式团队发布必须走审核状态机。
7. 权限不单独建表：谁能看、谁能装、谁能发，由 Skill 的归属与 `visibility`，加上 `organization_memberships` / `team_memberships` 里的角色推导出来。

### 1.4 发布事务建议

正式发布必须在一个数据库事务中执行下列逻辑：

1. 锁定对应 `skills` 行，防止并发发布同一个版本。
2. 确认版本处于 `pending_review`，扫描策略通过且审核权限满足要求。
3. 确认 `artifact_id` 所对应制品已上传、哈希校验完成、清单合法。
4. 将版本状态变更为 `published`，填充 `published_by`、`published_at`。
5. 更新 `skills.latest_version`，写入 `audit_events`。
6. 提交事务后发送通知事件；通知失败不能回滚已完成的发布，应通过事件/outbox 机制重试。

第 6 条现在的口径：**发布事务里不调任何外部通道**，因此不存在「通知失败把发布回滚」。整份设计里没有定义
通知渠道——§2.2 的接口清单里没有通知接口，全仓也没有邮件、webhook、站内信的配置与发送代码；审核队列
（`GET /reviews`）与审计事件（`audit_events`）就是现在给审核者的全部信号。等真有了渠道再补 outbox：建
`outbox_events` 表，发布事务里写一行，提交后由调度器投递，失败按退避重试——投递在事务之外，发布不会被
通知拖回去。在渠道出现之前不建这张表：一张没人读的表比没有表更难删。

### 1.5 不可变版本触发器

**已落地**：`apps/api/src/main/resources/db/migrations/V15__immutable_published_versions.sql`。
触发器守 `skill_versions` 的 UPDATE：状态已是 `published`/`revoked`/`yanked` 的版本，
`skill_id`、`version`、`artifact_id`、`source_commit`、`manifest_json` 一律不许改；状态字段本身
还能改成 `revoked`/`yanked`。

# 第二部分：接口规范

## 2.1 通用约定

### Base URL

- 本地开发：`http://localhost:8080/api/v1`
- 生产示例：`https://skills.example.com/api/v1`

### 身份认证

使用 Bearer Access Token。API 本身不接受用户提交的 `user_id` 作为身份依据。服务端通过 token 的 issuer/subject 映射用户。

令牌有两种来源，两套并存、互不影响：

- **外部 IdP（OIDC/OAuth 2.0）**：token 由外部 IdP 签发，issuer/subject 落在 `(oidc_issuer, oidc_subject)` 上。CLI 的登录流程优先采用 Device Authorization Grant 或浏览器 PKCE 流程；不要求用户把密码输入 CLI。
- **内置账号（用户名 + 密码）**：服务端自签 HS256 token，issuer 固定为 `skillmesh-local`，额外带 `uid` 与 `typ` 声明。`typ=access` 的才能当访问令牌用，`typ=refresh` 的只能拿去换新令牌——两者混用在认证层就被拒。

不部署外部 IdP 也能用：配好 `skillmesh.auth.jwt-secret` 即可，网页端与 CLI 都切到用户名密码登录。两种登录方式返回的令牌结构一致，客户端只有一套解析逻辑。

### 标准响应规则

- 成功读取：返回资源 JSON 或列表包装结构。
- 创建资源：`201 Created`，响应包含资源 ID 和 `Location`（适用时）。
- 异步扫描、发布、同步：`202 Accepted`，返回任务 ID/资源状态。
- 有并发版本控制的更新：要求 `If-Match` 或明确的 `expected_revision`。
- 可重试写请求：支持 `Idempotency-Key`。
- 限流响应：`429 Too Many Requests`，提供 `Retry-After`。
- 无权限或资源不可见时，私有资源可按安全策略统一返回 `404`，避免泄露资源存在性。

`Idempotency-Key` 的落地口径（服务端实现，不是建议）：键放在 `idempotency_keys` 表里，
唯一键是 `(user_id, scope, idem_key)`，`scope` 是「方法 + 路径」（去掉 `/api/v1` 前缀）。
同一个键再来一次，服务端把上次的响应原样还回去，不再建一份资源；
同一个键配了不同的请求体，回 `409 VERSION_CONFLICT`（键用错了）；
上一次还在处理中，回 `409 VERSION_CONFLICT`（稍后重试）；
上一次失败了，键会被放开，重试照常重来。

走这套机制的接口：`POST /skills`、`POST /skills/{skill_id}/versions`、
`POST /groups`、`POST /organizations/{organization_id}/invitations`。

其余带 `Idempotency-Key` 的接口本来就幂等，不用绕这张表：
`POST /devices`（同一台设备重复登记是同一条）、
`POST /installations`（同机同目录同 Skill 只有一条）、
`POST /sources/resolve`（只读不建资源）、
`POST /uploads/{upload_id}/complete`（会话已完成就原样还回去）。
`POST /sync/changesets` 另有一套：键按（设备，键）存在 `sync_changesets` 表上。

**客户端这一侧也要带**（CLI 已落地）：发布时 `POST /skills` 与
`POST /skills/{skill_id}/versions` 都带幂等键。键是「作用域 + 内容摘要 + 请求体」的
哈希：同样的内容重发是同一次请求（服务端把上次的响应还回来，不会多出一个版本），
内容变了就是另一次发布（键跟着变）。请求体只有元数据的建 Skill 请求还要把
内容摘要算进去——同样的元数据可能对应两次不同的发布。

### 错误响应结构

```json
{
  "type": "https://skills.example.com/problems/version-conflict",
  "title": "Version conflict",
  "status": 409,
  "code": "VERSION_CONFLICT",
  "detail": "The remote revision changed after the client read it.",
  "request_id": "req_01J...",
  "retryable": false,
  "field_errors": []
}
```

客户端应根据 `code` 分支处理，不应解析 `detail` 文本来判定业务状态。

| `GET` | `/keys/verify` | 制品签名公钥 | 免登录 |
| `GET` | `/config/public` | 登录前取 issuer 与 client_id | 免登录 |

`GET /skills` 的查询参数：

| 参数 | 说明 |
|---|---|
| `q` | 关键字，匹配名称、slug、描述。 |
| `visibility` | 按可见性过滤。 |
| `tag` | 按标签过滤（精确匹配）。 |
| `untagged` | `true` 时只返回没打标签的（与 `tag` 互斥）。 |
| `mine` | `true` 时只返回我名下的。 |

标签筛选的选项由 `GET /tags` 单独给：列表是游标分页的，从一页数据里汇总标签
汇总不全——用户想按一个只出现在第二页的标签筛选时，根本没有那个选项可点。
`GET /tags` 的口径与搜索一致（可见范围 + active），`mine=true` 时只统计我名下的。

**本地来源不进注册中心。** `skillmesh add --local <目录>` 与
`skillmesh install --file <zip>` 装的东西没有签名、没走过服务端的扫描与审核，
登记上去等于让未验证的内容冒充发布方的版本。它们只装到本机，来源写进锁文件
（`source_type: local`）。客户端遇到没有签名的版本本来就只标注「无签名」
而不阻断，签名闸不因此放松。

批量审核的语义：**逐条独立**。一条过了、另一条没过，两边都报清楚——服务端每条
在自己的事务里，共用一个事务的话第一条失败会把已经放行的也一起撤回来。
权限不放宽：每条照样走单条审核的那几道闸（reviewer 角色、不能审自己发布的
版本、扫描结论阻断），批量只是省了逐条点开详情页。响应形如：

```json
{
  "succeeded": [{"skill_id": "...", "version": "1.0.0"}],
  "failed": [{"skill_id": "...", "version": "2.0.0", "code": "FORBIDDEN", "message": "不能审核自己发布的版本"}]
}
```

### 2.2.1 审计动作清单

写进 `audit_events` 的动作：

| 动作 | 谁记的 | 含义 |
|---|---|---|
| `skill.created` | 服务端 | 新建 Skill（details 带 slug 与可见性） |
| `skill.updated` | 服务端 | 改元数据（details 带改了哪些字段） |
| `skill.archived` / `skill.restored` | 服务端 | 删除（软删除）/ 还原 |
| `skill.publish` | 服务端 | 发布了版本（个人直发在上传收尾，团队与组织在审核通过时） |
| `skill.submit_for_review` / `skill.publish_rejected` / `skill.publish_quarantined` | 服务端 | 送审 / 被驳回 / 被扫描隔离 |
| `skill.import_from_git` / `skill.update_from_git` | 服务端 | 从 Git 导入 / 从 Git 来源更新 |
| `version.submit` / `version.approve` / `version.reject` / `version.revoke` | 服务端 | 提交审核 / 审核结论 / 撤回 |
| `installation.register` / `update` / `refresh` / `unregister` | 服务端 | 安装登记的变动 |
| `sync.uploaded` / `sync.downloaded` / `sync.local_deleted` | 客户端上报 | 同步上传 / 拉取 / 本地随云端删除 |
| `install.completed` / `install.failed` / `install.upgraded` / `install.rolled_back` / `uninstall.completed` | 客户端上报 | 安装与卸载 |
| `sync.conflict_reported` / `sync.retried` | 客户端上报 | 冲突与重试 |

客户端能上报的动作是白名单（`AuditReportController.ALLOWED`），不在名单里的一律 400：特权动作（发布、撤回、权限变更）由服务端自己记，免得两套流水互相矛盾。上报时服务端还会确认上报者跟这个 Skill 真有关系（属主、组织或团队成员、装过它），否则任何登录用户都能往别人的流水里塞条目。

`sync.local_deleted` 只能由客户端报：云端删掉之后本地那份被移进回收站，这件事只有客户端看得见，服务端那边只有版本记录。

**本机操作日志**是另一回事：CLI 在本机把操作写进 `<缓存目录>/operations.log`（一行一条 JSON），记的是这台机器上的细节——同步把哪份移进了回收站、装到了哪个目录、哪一步失败了。服务端看不来的那些事靠它，`skillmesh logs` 看。

### 2.2.2 列表分页

数据量无界的列表一律用游标分页（`limit` + `cursor`，响应带 `next_cursor` 与 `has_more`）：

| 端点 | 排序键 |
| --- | --- |
| `GET /skills` | (updated_at, id) |
| `GET /deleted-skills` | (updated_at, id) |
| `GET /organizations/{organization_id}/invitations` | (created_at, id) |
| `GET /skills/{id}/versions` | (created_at, id) |
| `GET /audit-events` | (occurred_at, id) |
| `GET /reviews` | (submitted_at, created_at, id) |

审核队列的排序是三级，游标也得带三级：少了哪一级，同一时刻的多条待审顺序就不定，翻页会漏掉或重复。审计流水的主键是自增数字而不是 uuid（分区表的主键带分区键：`id` + `occurred_at`），游标用「时间 + 数字 id」单独一套编解码。

成员与团队列表（`/organizations/{id}/members`、`/teams`、`/teams/{id}/members`）仍是一次全量返回：它们的规模由组织人数决定，有界；真要上万成员的组织，得先换个模型，不是分页能解决的。

页面上「还有更多」要显式说出来：只拉一页却按总数显示，页面说的就是假话（§0.2）。

## 2.3 上传和下载协议补充

大制品走预签名 URL 或受控上传会话，API 服务不代理文件字节：服务端校验权限与版本号唯一性后发一个短时
有效的上传 URL（建议 5–15 分钟，限制方法、对象键与内容长度），CLI 上传到临时对象键；服务端校验归档路径、
文件数、解压后总大小、`SKILL.md`、文件摘要与恶意内容，通过后提升为不可变对象并登记 `artifacts`，不通过
则标记候选版本失败并清理临时对象。下载前再次鉴权，下载 URL 只用于短时访问，撤销权限后不得继续签发新 URL。

不要直接信任客户端提交的 manifest。服务端必须重新计算归档内实际路径和哈希，并与上传声明比对。

### 2.3.1 版本制品上传完整流程

1. `POST /skills/{skill_id}/versions` 创建 `draft` 候选版本，版本记录的 `artifact_id` 暂为空，返回 `upload_session_id`/上传 URL。
2. CLI 使用短时 URL 上传归档字节，不把对象存储凭据写入配置文件。
3. CLI 调用 `POST /uploads/{upload_id}/complete`。服务端验证字节数、SHA-256、压缩包路径与文件清单。
4. 校验通过后服务端创建 `artifacts` 记录并关联到版本记录；扫描在同一个事务里同步做完，按结论推进到 `pending_review`、`published` 或 `quarantined`——没有可观察的「扫描中」中间态。
5. 上传 URL 过期时，客户端重新申请上传会话；不得复用已失效或已完成的上传会话。

### 2.3.2 同步文件上传完整流程

1. `POST /sync/changesets` 创建待处理 changeset 并绑定 `device_id`、`skill_id`、`base_revision`。
   `manifest` 带的是**同步完成后的完整文件集**（不是只带变的文件）：
   服务端靠它跟基线版本做差，算出哪些文件要沿用基线、哪些要删。
2. 客户端只对变了的文件（新增或内容摘要不同）调用 `POST /sync/changesets/{id}/uploads`，
   服务端为每个相对路径创建短时上传会话。重传同一路径复用已有会话。
3. 客户端逐个上传文件并调用 `POST /uploads/{upload_id}/complete` 完成校验。
4. 客户端调用 `POST /sync/changesets/{id}/commit`，传入期望的云端 revision。
5. 服务端若发现云端 revision 已变化，返回冲突并保留双方版本；
   否则拿基线版本（`base_revision` 对上的那一版）的制品补齐没变的文件，
   与这次传上来的文件合成一份完整内容。
6. 合成结果的内容摘要要与 changeset 声明的 `local_hash` 对得上：对不上说明合错了，
   返回 409 且不发布——发布一份缺文件的版本比同步失败糟糕得多。
7. 本地删掉的文件不进 `manifest`，合成时从基线里去掉；删除要用户显式确认
   （`--allow-delete`），没有基线可比时不擅自传播。

## 2.4 权限矩阵建议

| 操作 | 个人所有者 | 团队 Member | Publisher | Reviewer | Org Admin |
|---|---:|---:|---:|---:|---:|
| 查看私有个人 Skill | 是 | 否 | 否 | 否 | 默认否，除非组织策略授权 |
| 安装团队可见 Skill | 按所有者权限 | 是 | 是 | 是 | 是 |
| 创建候选版本 | 是 | 否/按团队策略 | 是 | 默认否 | 是 |
| 审核版本 | 否/按职责分离 | 否 | 是 | 是 | 按策略 |
| 发布团队版本 | 个人空间不适用 | 否 | 是 | 是 | 是 |
| 撤回版本 | 个人版本可管理 | 否 | 按策略 | 否 | 是（组织 owner/admin） |
| 查看组织审计 | 否 | 否 | 否 | 按授权 | 是 |

「查看组织审计」这一行实际落地成三条：属主看自己 Skill 的流水；组织 owner/admin 看组织内 Skill 的流水；
审过某个 Skill 的 Reviewer 看这个 Skill 的流水。团队普通成员看不到流水——看得见 Skill 不等于能看它的撤回
与发布记录。实现见 `AuditService.canSeeAudit` 与 `AuditVisible.WHERE`（搜索与流水查询共用同一份可见性口径）。

两处实现比这张表宽，是有意的取舍：publisher 也拿到了审核权（「默认否」的「默认」二字就是说由组织策略定，
代码选了宽进），reviewer 通过审核即等于发布。双人复核的底线不靠角色档位，靠的是**不能审核自己发布的
版本**——这一条是硬约束。发布人与审核人是否必须不同，由组织安全策略决定。

# 第三部分：CLI 命令详细设计

## 3.1 CLI 目标与运行模式

二进制命名：`skillmesh`。命令在 Windows、macOS、Linux 上保持一致；Linux/macOS 可运行前台 Daemon，桌面系统可注册为系统用户服务。CLI 默认不需要管理员权限。

- CLI 负责一次性操作和交互：登录、搜索、添加来源、安装、检查更新、发布、回滚。
- Daemon 负责常驻操作：目录监听、自动同步、离线队列、定期检查更新。
- Agent 继续直接读取原生 Skill 目录，不依赖 CLI 在线运行。

### 3.1.1 配置路径

| 操作系统 | 配置与状态目录建议 |
|---|---|
| Linux | `${XDG_CONFIG_HOME:-~/.config}/skillmesh`；缓存使用 `${XDG_CACHE_HOME:-~/.cache}/skillmesh` |
| macOS | `~/Library/Application Support/SkillMesh`；缓存放 `~/Library/Caches/SkillMesh` |
| Windows | `%APPDATA%\\SkillMesh`；缓存放 `%LOCALAPPDATA%\\SkillMesh\\Cache` |

配置目录与缓存目录分开；凭据优先交给系统 Keychain/Credential Manager/libsecret 保存。配置文件只保存非敏感设置和凭据引用。

### 3.1.2 配置文件示例

`~/.config/skillmesh/config.yaml`：

```yaml
server: https://skills.example.com
profile: default
network:
  timeout_seconds: 30
  max_retries: 5
sync:
  enabled: true
  default_new_skill_policy: ask # ask | private | local_only
  default_update_policy: notify # manual | notify | auto_safe
  debounce_ms: 1200
  delete_protection_days: 30
  max_file_size_mb: 20
  max_total_size_mb: 50
security:
  block_detected_secrets: true
  reject_symlinks_outside_root: true
  allowed_git_protocols: [https, ssh]
agents:
  claude-code:
    enabled: true
    user_skills_dir: ~/.claude/skills
  codex:
    enabled: true
    user_skills_dir: ~/.codex/skills
  cursor:
    enabled: false
    user_skills_dir: ~/.cursor/skills
  # Hermes：按 agentskills.io 规范扫技能目录，扁平一层也能发现。
  hermes:
    enabled: true
    user_skills_dir: ~/.hermes/skills
    # 官方布局是 <category>/<name>/SKILL.md：分类取 SKILL.md 里
    # metadata.hermes.category 声明的值，没声明还是装成一层。
    category_dirs: true
  # 这个 Agent 额外的扫描根（全局的那份在 sync.extra_dirs）。
  extra_scan_dirs:
    - ~/.agents/skills
  # 扫这个目录时要不要递归进子目录。不填就是递归（沿用原行为）；
  # 目录是扁平的时候填 false，免得把技能自带的子目录也当成候选。
  recursive_scan: false
# 额外要扫的目录：项目级与自定义目录（设计文档 §6.1）。
# Agent 适配器给出的用户级目录默认就扫；这里放的是别的地方。
sync:
  extra_dirs:
    - ~/projects/app/.claude/skills
  # 本地删掉了整个 Skill，要不要也往云端传删除（软删除）。
  # 默认 false：目录扫不到不等于用户删了它。
  propagate_delete: false
```

路径只是默认值，可通过 `skillmesh agents detect` 检测实际环境，并由适配器按 Agent 当前版本验证。不要把上述配置目录视为所有 Agent 版本永久不变的硬编码事实。

## 3.2 全局参数

| 参数 | 说明 | 范围 |
|---|---|---|
| `--server URL` | 覆盖服务端地址。 | 全局 |
| `--json` | 输出稳定 JSON，供脚本调用。 | 全局 |
| `--quiet` | 减少普通提示，但错误仍输出到 stderr。 | 全局 |
| `--profile NAME` | 使用指定配置档：配置目录下的 `profiles/<名字>.yaml`，叠在 `config.yaml` 之上，只写要改的项。 | 全局 |
| `--project PATH` | 指定项目根目录；默认从当前目录向上查找 `.git` 或 `skillmesh.yaml`。 | 全局 |
| `--agent NAME` | 目标 Agent：`claude-code`、`codex`、`cursor`、`generic`、`all`。 | 全局 |
| `--scope user\|project\|custom` | 安装范围。 | 全局 |
| `--verbose` | 输出诊断日志并显示平时隐藏的完整绝对路径；敏感字段始终脱敏。 | 全局 |
| `--no-color` | 禁用 ANSI 色彩。 | 全局（本 CLI 输出本来就没有色彩） |
| `--yes` | 对可安全自动确认的提示采用默认值；不得绕过安全阻断、权限或破坏性覆盖。 | 全局（当前没有可自动确认的提示） |
| `--dry-run` | 只显示计划，不写入本地文件、不提交云端状态。 | 全局 |
| `--timeout DURATION` | 命令整体超时，例如 `30s`、`2m`（单个请求的超时是配置里的 `network.timeout_seconds`）。 | 全局 |

全局参数的几条口径：

- **配置档**（`--profile`）是叠在 `config.yaml` 之上的一层，只写要改的项：空值等于没写，基础配置原样保留。`agents.<名字>.enabled` 是例外——它按「写了就算」处理，因为布尔零值分不出「没写」与「显式关掉」。配置档文件放在配置目录的 `profiles/<名字>.yaml`，指名要一个不存在的档是错（退 2），不静默退回基础配置。
- **项目根目录**（`--project`）默认从当前目录向上找带 `.git` 或 `skillmesh.yaml` 的目录。在仓库的子目录里跑命令时，锁文件与项目级安装目录跟着仓库走，不跟着当前子目录走。
- **整体超时**（`--timeout`）是命令级的截止时间，跟配置里的 `network.timeout_seconds`（单个请求的超时）是两回事。超时到了整个命令停，退出码按错误类型算。
- **目标 Agent**（`--agent`）与**安装范围**（`--scope`）是全局参数，但每个命令仍保留自己的默认值：用户没给时，`install`/`group install` 装到 `claude-code` 的 `user` 范围，`add` 有项目根时装到 `project`，`scan`/`sync` 用全部启用的 Agent。`install` 沿用锁文件里的旧值（上次装到哪就装到哪）时看的是「用户这次给没给」——没给 `--agent` 才沿用。
- **演练**（`--dry-run`）是全局参数，但只有认它的命令才生效：`install`、`add`、`group install`、`sync`、`publish`、`share`、`update`、`fix-skill` 支持演练；其余命令收到 `--dry-run` 会在 stderr 提示「该命令暂不支持 --dry-run，会照常执行」——让人以为演练过、实际动了数据，比报错更坏。
- **演练的承诺是「什么都不改」**：不写本地文件、不传云端、不改同步基线。`sync` 撞上冲突时也一样——演练只说会怎么做（保留本地 / 保留云端 / 先按文件合并），不会真上传、真下载，合并结果也不写回本机（本地文件被改了，用户看到的演练结果就不是他机器上的样子了）。

退出码：

| 退出码 | 含义 |
|---:|---|
| `0` | 成功，无需额外处理。 |
| `1` | 未分类错误。 |
| `2` | 参数或配置错误。 |
| `3` | 未登录/认证失败。 |
| `4` | 权限不足。 |
| `5` | 网络或服务端不可用，可按 `retryable` 判断是否重试。 |
| `6` | 安全策略阻断。 |
| `7` | 检测到冲突，需要人工处理。 |
| `8` | 目标 Agent 或目录未检测到/不可写。 |
| `9` | 目标资源不存在。 |

机器可读模式应输出 JSON 到 stdout；日志和交互提示写入 stderr。不能在 stdout 混入进度条或 ANSI 控制字符。

实现约定：

- `--json` 目前覆盖 `list`、`search`、`info`、`installations`、`logs`、`scan`、`doctor` 七个命令；其余命令加了 `--json` 会在 stderr 提示「暂不支持」，输出仍是人读格式。
- 失败一律写 stderr，stdout 只留给成功结果。JSON 模式给一个信封：`{"ok":false,"code":…,"message":…,"exit_code":…,"details":…}`；人读模式给一行「错误: …」。
- 错误码沿用服务端 problem+json 的口径，不另造词表——同一个 `code` 在服务端和 CLI 里指的是同一件事，脚本不用记两套映射。
- 参数个数或 flag 写错时退出码是 `2`，信封里 `code` 是 `INVALID_ARGUMENTS`。
- 退出码由错误类型推出：服务端的 `FORBIDDEN` 退 4、`NOT_FOUND` 退 9、`SYNC_CONFLICT` 退 7、`RATE_LIMITED` 退 5，认证失败退 3；没登记的错误码退回按 HTTP 状态判断。


## 3.3 登录与身份

### `skillmesh login`

用法：

```bash
skillmesh login
skillmesh login --server https://skills.example.com
skillmesh login --server https://skills.example.com --device-code
skillmesh login --server https://skills.example.com --username alice
skillmesh login status
skillmesh register https://skills.example.com --username alice
skillmesh logout
```

行为：

1. 走外部 IdP 时：打开系统浏览器，使用 OIDC 授权流程；无浏览器环境时显示 Device Authorization URL 和一次性 code。
2. 走内置账号时：`--username` 加 `--password` 登录；不给 `--password` 就从终端无回显读取，也可用 `SM_PASSWORD` 环境变量。服务端不部署 IdP 时这条是唯一路径。
3. CLI 获取短期访问令牌及刷新令牌，令牌存入系统凭据库。
4. 使用 `/me` 验证令牌并展示当前账号、组织和角色。
5. `logout` 撤销服务端会话（若支持），清理本地凭据引用；不删除本地 Skill。

`register` 注册内置账号：用户名唯一（不区分大小写），密码最短 8 位、最长 72 位（72 是 BCrypt 的硬上限）。服务端不开放自助注册时（`skillmesh.auth.allow-register=false`）返回 403，由管理员建号。

安全规则：不把 Bearer Token 放在命令行参数中，避免进入 Shell 历史与进程列表。`--password` 虽可用，但属于兜底手段，优先用终端无回显输入或环境变量。

## 3.5 Git 来源解析、添加与安装

### `skillmesh source resolve`

```bash
skillmesh source resolve https://github.com/owner/agent-skills
skillmesh source resolve https://git.example.com/team/skills.git --path skills/java-debug --ref v1.2.0
```

行为：解析规范化仓库 URL、ref 实际 commit，并扫描候选 Skill 目录；仅列出符合目录规范的候选项。私有仓库必须使用凭据管理器中的凭据引用。服务器侧解析和本地直接 clone 模式由部署策略决定；无论在哪执行，都必须做路径与资源限制校验。

### `skillmesh add`

用途：从 Git 仓库安装 Skill 到 Agent 目录。默认就装，`--dry-run` 只看不装。

```bash
skillmesh add https://github.com/owner/agent-skills
skillmesh add https://github.com/owner/agent-skills --path skills/java-debug
skillmesh add https://github.com/owner/agent-skills --path skills/java-debug --ref v1.2.0
skillmesh add git@git.example.com:team/skills.git --path skills/release --ref main --credential-ref corp-git
```

参数：

- `--path PATH`：仓库子目录。仓库只有一个候选 Skill 时可省略；多个候选 Skill 时必须选择或交互确认。
- `--ref REF`：可与 `--ref-type branch|tag|commit|default` 搭配；默认使用仓库默认分支。
- `--agent NAME`：目标 Agent；`all` 只安装到已启用且检测通过的适配器。
- `--scope user|project|custom`：默认 `project`（若检测到项目根目录），否则提示用户。
- `--dry-run`：只列出会装什么，不实际安装（默认就装）。
- `--update-policy manual|notify|auto-safe`：默认 `notify`。
- `--credential-ref REF`：本机凭据管理器中的凭据引用，不接受明文 token。
- `--name NAME`：本地覆盖显示名，仅作别名，不改变上游 Skill 元数据。

输出必须包括规范化仓库 URL、子目录、解析 commit、安装路径、摘要与扫描结论。风险扫描失败时默认阻断安装；仅有低风险 warning 时可根据策略要求显式确认。

### `skillmesh install`

```bash
skillmesh install java-service-debug --agent claude-code --scope project
skillmesh install https://github.com/owner/repo --path skills/db-migration --agent codex
skillmesh install java-service-debug --version 1.2.0 --agent all --dry-run
```

支持来源类型：

- SkillMesh 云端 Skill ID/slug。
- 已登记的本地来源名。
- Git URL + 可选子路径与 ref。

安装事务：

1. 解析 Skill 来源并确认版本/commit。
2. 下载到缓存临时目录。
3. 校验压缩包和文件路径，拒绝路径穿越、目录外符号链接、超大文件与禁用文件。
4. 校验文件清单/摘要并执行本地安全扫描。
5. 生成安装计划并检测目标目录的同名 Skill。
6. 同名未受 SkillMesh 管理时，默认不覆盖；可用 `--replace` 进入交互式备份/冲突流程。
7. 复制到临时目标目录，原子切换至最终目标路径；记录来源、版本与摘要。
8. 注册安装实例；注册服务暂不可用时标记为待上报，不撤销已经校验成功的本地安装。

## 3.6 本地 Skill 扫描与无感同步

### `skillmesh scan`

```bash
skillmesh scan
skillmesh scan ~/.claude/skills --agent claude-code
skillmesh scan --all-agents --json
skillmesh scan --include-unmanaged --dry-run
```

默认扫描配置中已启用的 Skill 根目录。输出新发现、已管理、内容变化、路径冲突、被忽略、疑似敏感文件等分类。不应扫描整个用户目录，也不应将无法访问目录当作空目录并据此同步删除。

### `skillmesh sync`

```bash
skillmesh sync
skillmesh sync --skill java-service-debug
skillmesh sync --direction upload --skill java-service-debug
skillmesh sync --direction download --skill team-release-checklist
skillmesh sync --all --dry-run
skillmesh sync --resolve keep-local --conflict <conflict-id>
```

参数：

- `--direction upload|download|both`：同步方向，默认 `both`。
- `--skill ID_OR_NAME`：指定一个 Skill。
- `--all`：处理所有已授权同步项。
- `--resolve keep-local|keep-cloud|keep-merged|keep-both`：解决指定冲突；`keep-merged` 需要本地合并文件并重算摘要。
- `--conflict ID`：指定待解决冲突。
- `--propagate-delete`：把「本地删掉了整个 Skill」也往云端传（软删除）。默认不传——目录扫不到不等于用户删了它。
- `--force-delete`：配合 `--propagate-delete` 用，确认「本地目录是真的被清空了」，不是临时不可用。见下面「反方向」一节。
- `--force`：只允许在交互确认并有可回滚快照的情况下用于覆盖；不能绕过安全扫描和权限校验。

同步机制：

1. 本地文件事件触发防抖扫描，而不是直接上传单个 watcher 事件。
2. 计算规范化文件 manifest；过滤 `.git`、缓存、临时文件和敏感路径。
3. 与 `base_revision`、本地 manifest、云端 manifest 比较，形成 changeset。
4. 使用 `Idempotency-Key` 提交 changeset；重复重试不得重复创建云端版本。
5. 云端返回冲突时不自动覆盖，写入本地冲突状态和解决建议。
6. 上传失败进入持久队列；退避重试并在达到上限后给出可诊断错误。
7. 删除默认使用软删除/回收期；只有明确配置并确认后才传播删除。
8. 同步结束后体检云端已发布版本的制品：不是 zip 的当场报出来，提示确认后撤回。撤回不可逆，CI 等无输入环境只报告不动手。服务端「只收 zip」的闸门上线前，这层检查是兜底。

### `skillmesh watch`

```bash
skillmesh watch start
skillmesh watch status
skillmesh watch pause
skillmesh watch resume
skillmesh watch stop
```

在前台可由 `skillmesh watch run` 托管；生产桌面/开发机环境建议用 `skillmesh watch install` 注册开机自启。`watch pause` 只暂停后台同步，不影响 Agent 读取现有 Skill 文件。监听启动时做全量 reconcile，以弥补文件系统通知丢失。

### `skillmesh watch install` / `uninstall` / `logs`

```bash
skillmesh watch install
skillmesh watch uninstall
skillmesh watch logs --tail 200
```

服务安装/卸载操作必须只更改用户级服务配置，不默认要求 root/管理员权限。若操作系统不支持服务注册，可保留前台运行模式。

### `skillmesh share`

```bash
skillmesh share codex --from claude-code --dry-run
skillmesh share codex --from claude-code
```

让一个 Agent 复用另一个 Agent 的那份技能内容：实体只存一份，其余 Agent 的目录里每个技能换成一个指向它的链接。磁盘占用从「几份」变成「一份」，同步条目数也跟着回到实际份数。

设计口径：

- 共享粒度是**每个技能一个链接**，不是把整个 Agent 目录换成链接——Agent 自己的目录（Codex 的 `.system` 之类）不能被搬走。
- 目标目录独有的技能先搬到源目录（那边才是实体）；两边内容一样的删掉目标目录里那份；源目录有而目标目录没有的补上链接；**同名但内容不同**的停下来报错，不自动选边。
- 链接放在哪儿按**目标 Agent 自己的规则**算：分类分层的 Agent（Hermes 的 `<category>/<name>/`）放分类下面，与安装时同一套规则——放平了等于同一个技能装了两份。
- 扫描与同步按**实体路径**去重：目录级链接与技能级链接都要解析到真实文件，否则同一份内容会被算成好几种，同步条目数翻倍。
- 删除传播按实体路径判断「这份文件还在不在」：共用目录时删掉一份就是要传删除到云端，不能因为「别处还有同名」而漏传；但同名而**不是同一份**（云端删过又重建）时仍按保守处理，不误删云端那份。
- 写操作落在链接指向的真实目录上，链接本身保留；Agent 读到的始终是同一份内容。

### 技能统一目录（sync 内置）

```yaml
# config.yaml
sync:
  shared_dir: ~/.agent/skills   # 默认值；配成空串等于关掉
```

```bash
skillmesh sync --no-share   # 这一次不整理
```

`sync` 在对账之前先做一遍目录整理：各 Agent 目录里的技能**实体**搬进 `sync.shared_dir`，原位置换成指向它的链接。实体只存一份，Agent 目录里是视图。

设计口径：

- **只搬实体目录**。已经是链接的一律不碰：链接多半是别的工具（magpie 这类技能管理器）建的，实体归谁管是那个工具的事——抢过来搬走，它自己的链接就全成了死链。
- **共享目录里原本就有的技能不收编**。判断依据是「这个技能在某个 Agent 目录里出现过没有」：出现过的才算 skillmesh 管的，才往别的 Agent 目录补链接；没出现过的（用户自己放在共享目录里的）不塞进 Agent 目录，也就不会被拉进同步范围白传到云端。
- 整理放在对账之前，改完目录结构要**重新扫描**：后续同步条目用的是统一之后的路径。
- 整理是幂等的：跑第二遍没有实体可搬，也没有链接可补。
- 链接优先用符号链接，Windows 上退而求其次用目录联接；删掉链接即还原成普通目录。

## 3.7 检查更新、预览、更新与回滚

### `skillmesh update --check`

```bash
skillmesh update --check
skillmesh update --check --all
skillmesh update --check --skill java-service-debug --json
```

只查询远端 ref 与当前安装版本的差异，不改本地文件。输出 current/latest commit、版本、差异文件、风险变化、许可证状态、是否存在本地修改以及是否可自动升级。

### `skillmesh update`

```bash
skillmesh update java-service-debug
skillmesh update --all
skillmesh update java-service-debug --to 1.2.0
skillmesh update java-service-debug --to-commit 4d39a2f
skillmesh update --all --policy auto-safe --dry-run
```

规则：

- `--to VERSION` 与 `--to-commit SHA` 互斥。
- 固定到 commit/tag 的来源不会静默跟随分支；显式指定目标版本/commit 才升级。
- `manual` 策略不执行自动升级；`notify` 仅提示；`auto-safe` 只在无本地修改、扫描通过、签名/摘要验证通过且无新增高风险能力时执行。
- 更新前创建本地回滚点或确保可重新获取原版本。
- 目标目录有本地改动时停止自动更新，可生成 diff 或使用 `--save-local-changes` 创建本地补丁。
- 安装完成后重新计算摘要并注册新安装状态；失败时原子回退到旧版本。

### 回滚到旧版本

回滚不单设命令——用 `install` 指定版本号即可：

```bash
skillmesh install java-service-debug --version 1.1.0
skillmesh install java-service-debug --version 1.1.0 --dry-run
```

锁文件里记着这个 Skill 的来源与安装位置，`install <名字> --version <旧版本>` 会装回那一版，
不用另记一个 `rollback` 命令。回滚只变更本机安装内容，不会将旧版本重新发布到云端，
也不会更改 Git 上游。若目标版本已被安全撤回，应默认拒绝回滚；只有具备权限并显式使用
经组织策略允许的安全例外时才可安装已撤回版本，且必须写本地与服务端审计事件。

### 网页端从 Git 来源更新

从 Git 装过、并且发布到云端的 Skill，`skill_sources` 里有它的来源（仓库、子目录、ref、已落地的 commit）。控制台「我的 Skill」的详情面板据此给出一条在线更新路径：

| 步骤 | 端点 | 行为 |
| --- | --- | --- |
| 看来源 | `GET /skills/{skill_id}/source` | 返回仓库、ref 与当前 commit。没有 Git 来源的返回 404，界面不显示这一块。 |
| 查更新 | `POST /skills/{skill_id}/source/check-updates` | 服务端 `git ls-remote` 比对远端 ref，只报差异，不下载内容。 |
| 拉新版 | `POST /skills/{skill_id}/source/update` | 浅克隆远端 → 定位子目录 → 按 CLI 同一套规则挑文件打包 → 建候选版本 → 服务端扫描 → 个人与公开直接发布，团队与组织进待审队列。 |

### 从 Git 导入 Skill

有些 Skill 是直接下下来的，没有进过控制台，也没有来源记录。控制台「我的 Skill」提供「从 Git 导入」，一次做完建 Skill、记来源、发首个版本三件事：

| 步骤 | 端点 | 行为 |
| --- | --- | --- |
| 探仓库 | `POST /sources/resolve` | 浅克隆一次，列出仓库里哪些目录像 Skill（带 `SKILL.md`），供人挑。 |
| 导进来 | `POST /sources/import` | 建 Skill → 写 `skill_sources`（来源类型 `git`、仓库、子目录、ref、commit）→ 按 CLI 同一套规则打包 → 发 `1.0.0`。 |

两条链路的共同约束：

- **权限与发版一致**：个人与公开只有属主能拉，团队与组织要 publisher 及以上。拉新版就是发版。
- **只改云端**：服务端看不到任何人的磁盘。本机装的那份要靠 CLI 的 `skillmesh update` 拉回去。
- **只支持公开仓库**：服务端没有客户端的凭据，`credential_ref` 只是个引用。私有仓库只能用 CLI 在本机更新。
- **版本号要避撞**：待审与草稿的版本号没进 `latest_version`，算新版本号时要把它们算进去，撞唯一约束就是 500。
- **服务端要能出网**：访问不了 GitHub 时给服务端配代理（`SM_GIT_PROXY`，或容器自身的 `HTTPS_PROXY`）。
- **走同一条发布链路**：打包、扫描、审核、`latest_version`、回收站跟手发的一模一样，不另开一条捷径。导入时路径写错会在克隆后报错，不会留下空 Skill；frontmatter 的扩展元信息（`license`、`author`、`platforms`、`tags`、`metadata.*`）一起带进 Skill 的 `metadata`，与 CLI 发布同一套口径。

### SKILL.md 规范（agentskills.io）

按规范扫的 Agent（Hermes 等）只认合规的 SKILL.md：不合规的装上去也不会被扫到。
规范就几条硬要求，两侧都守着：

| 要求 | 限制 | 谁守 |
| --- | --- | --- |
| frontmatter | 文件开头是 `---`，闭合的 YAML 映射 | CLI 装前 + 服务端扫描 |
| `name` | 必填，≤ 64 字符 | 同上 |
| `description` | 必填，≤ 1024 字符 | 同上 |
| 正文 | frontmatter 之后非空 | 同上 |
| 文件大小 | 整文件 ≤ 100,000 字符 | 同上 |

- **CLI 侧**：`skillscan.ValidateSpec`，装与发之前都过；不合规直接报错说清缺什么。
- **服务端侧**：扫描器的一条阻断规则。绕开 CLI 直接调 API 上传同样拦得住——
  合规与否由服务端说了算。
- **不合规的版本进隔离**（quarantined），不是被悄悄发出去。
- **存量老 Skill**：`skillmesh fix-skill <目录>` 补齐 frontmatter（`name` 取目录名，
  `description` 取正文第一段）；改不了源文件的第三方 skill 可在 frontmatter 里写
  `metadata.skillmesh.spec_exempt: true` 声明豁免，两侧同一套口径。
- **扩展字段**：frontmatter 里的 `platforms` / `tags` / `license` / `author` /
  `metadata.hermes.*` 随发布上云（进 skill 的 `metadata`），网页端可见。
  批量导入时 `name` 与 `description` 也取自 frontmatter——那是 skill 自己声明的。
- **分类分层**：Hermes 的官方布局是 `<category>/<name>/SKILL.md`。分类取
  `metadata.hermes.category`，只对开了 `category_dirs` 的 Agent 生效；
  装完的实际路径记进锁文件的 `target_paths`，`list` / `uninstall` 用它，
  不按配置重算（Agent 目录改了以后重算会卸错地方）。

## 3.8 发布与审核

### `skillmesh publish`

```bash
skillmesh publish ./skills/java-debug
skillmesh publish ./skills/java-debug --version 1.2.0 --channel stable
skillmesh publish ./skills/java-debug --visibility private --dry-run
skillmesh publish ./skills/java-debug --org engineering --team platform --submit-review
```

推荐流程：

1. 本地验证目录和 `SKILL.md` 元数据。
2. 生成临时归档和逐文件 manifest。
3. 执行本地敏感信息与危险操作扫描。
4. 通过 API 创建候选版本并上传制品。
5. 服务端重新解包计算摘要、执行扫描、检查来源与许可证规则。
6. `--submit-review` 将版本转入审核；个人私有草稿可按策略免团队审核，但依旧不能跳过安全检查。
7. 只有有发布权限的主体才能发布组织/团队版本。

`--visibility public` 只能用于用户明确授权公开的操作；需要交互提示确认，不能被 `--yes` 自动弱化。


### `skillmesh cloud delete` / `restore` / `deleted`

删掉云端的 Skill 是**软删除**：版本、制品、安装记录都留着，Skill 不再出现在列表里也不能被安装，回收期内可以还原。归档之后 slug 让了出来——可以用同一个名字重建一个新的。

```bash
skillmesh cloud delete <slug>       # 删（归档）
skillmesh cloud deleted             # 看自己删过哪些
skillmesh cloud restore <slug>      # 还原
```

`delete` 走 `DELETE /api/v1/skills/{id}`，`restore` 走 `POST /api/v1/skills/{id}/restore`，`deleted` 走 `GET /api/v1/deleted-skills`。已删除清单单独一个路径而不是 `/skills/deleted`——后者会被 `GET /skills/{skill_id}` 抢走（`skill_id` 是变量，"deleted" 被当 UUID 解析，报出来的是「参数格式不对」）。

删除权限与发布权同档：个人 Skill 只有属主能删，团队/组织的要 publisher 及以上。

**删完各端会自己跟上**：下一次 `skillmesh sync` 看到云端明确删过了，就把本地目录移进本机回收站（`skillmesh trash list` 能找回），并清掉这条同步基线。同步只认服务端明确记下的删除——不会靠「云端查不到」去推断：换台服务器、连了个空库，都不会把本机的 Skill 误删。

**删除的传播按 slug 判，不只看本机基线**。清单以 slug 为键（本地这份是哪个 Skill 只能靠 slug 认，基线里的 skill_id 可能压根没有这条记录——别的机器上装的、刚复制进来的都是）：

| 本机这份 | 处理 |
| --- | --- |
| 基线里的 skill_id 与删除记录一致 | 移进本机回收站，清掉基线 |
| 对不上（别的机器的副本、基线没记过、同名的另一个 Skill） | 本地保留但**不上传**——云端删过，上传就是复活 |
| 对不上，且云端这个 slug 上已经有活着的 Skill | 删除记录已过时（删掉之后又用同名重建过），按普通三方对账处理 |

先按 slug 拦住上传、再决定删不删本地，顺序不能反：反了就先把删掉的传回云端了。
删除记录会过时——归档让出了 slug，别人（或用户自己）能用同一个名字重建一个新的。按 slug 查一次云端
（搜索只返回 status=active 的 Skill，归档的查不到），有活的就当删除记录过期。

**反方向：本地删掉了整个 Skill，云端也删**（`sync --propagate-delete`，或配置 `sync.propagate_delete: true`）。

默认不做。目录扫不到不等于用户删了它——路径变了、网盘没挂上、Agent 目录搬了家，这几种情况扫不到都是「本地没了」，但云端该留着。开了之后按「本地确实删了」判定，四条同时满足才动云端：

| 判定 | 说明 |
| --- | --- |
| 基线里记着云端 Skill 的 id | 没记的说明它不是从这台机器传上去的，云端没有对应的东西可删（更不能删别人的） |
| 基线记的路径确实没了 | 目录还在就不算删 |
| 本机别处没有同一份 | 同一个 Skill 装在多个 Agent 目录下、或挪到了别的扫描目录，都不算删 |
| 路径还在本次扫描范围内 | 改了 Agent 目录、删了自定义目录之后，老路径扫不到不算删 |

云端那边走软删除（`DELETE /skills/{id}` 归档），回收期内可 `cloud restore` 还原。删除必须赶在拉取之前：云端还留着它的话，会被当成「云端有、本机没有」又装回来，删了等于没删。

**目录「看不清」时不删也不装**。上面的判定只看「本地这份没了」，但扫描根整个不可用
（网盘掉了、目录被搬走、权限变了）时扫不到东西不等于用户删了它——照着「全没了」
往云端传删除，一次就能把整个目录的 Skill 从云端清掉。两种情况算「看不清」：
目录列不出来；目录里一个 Skill 都不剩而基线里本来有（用户删东西是一个个删的，
不会一次全没）。这两种情况下：

- 不往云端传删除，结果里明说「本地目录看起来整个没了，没往云端传删除」。
- 也不把云端那份装回来：装进去的那份用户根本看不见，「本机没有」这个状态还变了，
  下一轮又会当成云端新增再装一遍。

代价是「用户真的把整个目录清空了」也传不上去——那种情况云端留着，本机下一轮
又拉回来。要传就显式说一声：`--propagate-delete --force-delete`
（确认目录真被清空了），或逐个 `skillmesh cloud delete <slug>`。

**拿不到「已删除清单」就不上传**：`sync` 开头先拉 `GET /api/v1/deleted-skills`。拉不到（服务端版本太旧、没有该端点，或网络不通）时，本次同步一个都不上传，直接报失败。理由是三方比较里「云端查不到」本来就判成「该上传」——没有删除概念时这没问题，有了删除语义后照旧上传就会在云端新建一个同名的 Skill，把删掉的复活。拿不到清单就是「不知道云端删了什么」，此时上传不安全。

### `skillmesh cloud revoke`

撤回云端的**某一个版本**：Skill 还在，只是这一版不再对外可用——装不上，也不能被送审或转正。

```bash
skillmesh cloud revoke <slug> <version> --reason "制品发错了"
```

走 `POST /api/v1/skills/{id}/versions/{version}/revoke`，只有属主能撤回自己的版本。撤回**不可逆**：要恢复只能发一个新版本。制品与文件仍留在云端，只是不再对外可用；已经装到别人机器上的内容不被无声删除，他们下次同步会看到撤回提示。

撤回原因记进服务端审计流水（`version.revoke`），本机操作日志也记一条同名动作。

## 3.10 项目级配置与锁文件

项目根目录可包含：

```text
project/
├── skillmesh.yaml
├── skillmesh.lock.yaml
└── .agents/skills/...
```

`skillmesh.yaml` 示例：

```yaml
version: 1
skills:
  - name: java-service-debug
    source:
      type: git
      repository: https://github.com/example/agent-skills.git
      path: skills/java-debug
      ref_type: tag
      ref: v1.2.0
    install:
      agents: [claude-code, codex]
      scope: project
    update_policy: notify
```

`skillmesh.lock.yaml` 示例：

```yaml
version: 1
resolved_at: "2026-10-19T10:00:00Z"
skills:
  - name: java-service-debug
    source_id: "<source-id>"
    repository: https://github.com/example/agent-skills.git
    path: skills/java-debug
    ref_type: tag
    ref: v1.2.0
    resolved_commit: "<full-commit-sha>"
    version: 1.2.0
    sha256: "<artifact-sha256>"
    agents: [claude-code, codex]
    installed_hash: "<本机内容的摘要>"
    scope: project
    # 每个 Agent 的实际安装路径。卸载按它来，不按配置重算。
    target_paths:
      claude-code: ~/.claude/skills/java-service-debug
      codex: ~/.codex/skills/java-service-debug
```

项目级安装按 lock 文件复现，除非用户执行 `skillmesh update` 或 `skillmesh lock refresh`。CI 环境建议执行 `skillmesh install --locked`：如果远端解析结果与 lock 文件不符则失败，防止构建环境静默漂移。

### 3.12 让 Agent 调用 CLI

Agent（Claude Code、Codex 等）要能查、装、发 Skill，前提是它能稳定找到 CLI，
并且知道哪些操作不能自己做。两条都要定死：

**固定可发现路径。** CLI 自己把自己发布到 `<配置目录>/bin/skillmesh`（Windows 上
带 `.exe`），旁边写一个 `.version` 标记。协议只有一条：**复制成功之后才写标记**。
Agent 侧据此判三态——有标记 = 完整可用；只有二进制没有标记 = 上次复制没成功，
不可用；都没有 = 还没发布过。PATH 上的 `skillmesh` 可能是别的版本，要用
`--version` 确认。

```bash
skillmesh self-install            # 发布
skillmesh self-install --check    # 只看状态
```

**操作契约。** `apps/cli/skills/manage-skills/SKILL.md` 是给 Agent 读的操作契约，
带 frontmatter，装进 Agent 的 skills 目录即可被自动加载。契约里写清三件事：
心智模型（库 / 可见性 / 版本 / 审核）、不可逆操作要人工确认、**不得执行
`review approve`**——审核人不能审自己发布的版本是双人复核的底线，让 Agent 自动
审批等于绕开它。

# 第四部分：安全、测试与开发验收

## 4.1 服务端必须校验的事项

- 身份、组织成员关系和对象级权限。
- Git URL 协议、主机、重定向目标和访问目标 IP；防止 SSRF、访问云元数据地址和回环网络。
  白名单主机与 DNS 校验只管得住初始 URL：`git` 自己还会再解析一次，那段时间差里
  DNS 换成内网地址就绕过去了（DNS rebinding）。所以校验通过的地址要钉给 git——
  `https` 用 `http.curloptResolve`，`ssh` 用 `HostName` 指到那个地址并用
  `HostKeyAlias` 保住按域名的主机密钥校验；HTTP 重定向一律关掉。
- 压缩包路径穿越、符号链接、硬链接、大小、文件数、解压后总大小及压缩比。
- 制品必须是 zip 归档且根目录有 `SKILL.md`：Java 的 `ZipInputStream` 对不是 zip 的字节**不报错**（它扫不到本地文件头就返回空清单），一份 tar.gz 或一段错误页会被当成「空制品」发布出去，直到客户端安装时才炸（Go 的 `archive/zip` 是严格的）。发布这道闸得自己把住。
- 制品摘要必须由服务端对实际字节重新计算。
- `SKILL.md` frontmatter 与目录格式校验；不信任客户端上报的扫描结果。
- 对象存储预签名 URL 时限、权限、对象键和写入方法范围。
- 审核、发布、撤回必须记录审计事件。
- 请求限流、文件上传限额、下载并发限制和 Git 获取超时。

「下载并发限制」的落地口径：走 `disposition=stream` 的下载要占一个名额
（`skillmesh.artifact.max-concurrent-downloads`，默认 8），满了立刻返回
HTTP 429 + `RATE_LIMITED` + `Retry-After`，不排队——排队等下去只会占满 Web 容器的工作线程。
预签名直链（`disposition=redirect`）不经服务端，不占名额。名额跟着流走：响应写完或客户端断开，
流被关掉，名额就还回来。

## 4.2 CLI 必须校验的事项

- 本地路径规范化，安装/删除目标必须位于配置的 Agent 根目录或用户明确授权的自定义根目录内。
- 不跟随目录外部符号链接；不覆盖未由 SkillMesh 管理的同名目录，除非用户明确执行替换流程。
- 更新前检查本地差异并保存回滚点。
- Token 存储在系统凭据库；日志不包含敏感请求头或 URL 中的凭据。
- 同步使用幂等键；重试不重复应用删除或重复创建版本。
- 不将用户工作文件的绝对路径、文件内容和 Git 私有 URL 无限制发送到遥测系统。

## 4.4 统一错误码

下面是**服务端实际会发的错误码**（`apps/api/.../common/ErrorCodes.java`）。
§2.1 要求客户端只按 `code` 分支，就用这张表：

| 错误码 | HTTP | 可重试 | 处理建议 |
|---|---:|---|---|
| `VALIDATION_FAILED` | 400（参数校验类的少数是 422） | 否 | 根据 `field_errors` 修正参数。 |
| `NOT_FOUND` | 404 | 否 | 检查 ID/slug 及可见性。 |
| `FORBIDDEN` | 403 | 否 | 检查组织角色与资源权限。 |
| `VERSION_CONFLICT` | 409 | 取决于场景 | 重新读取资源并让用户确认。 |
| `DIGEST_MISMATCH` | 422 | 否 | 丢弃制品并重新打包/下载。 |
| `ARTIFACT_MISSING` | 410/422/502 | 否 | 制品已被清理、key 不对或对象存储取不到，重新上传。 |
| `SLUG_TAKEN` | 409 | 否 | 换个 slug，或用 `--org/--team` 重发已有的那个。 |
| `INVITATION_INVALID` | 409 | 否 | 邀请已过期、撤销或已被用掉，重新生成。 |
| `INVALID_CREDENTIALS` | 401 | 否 | 用户名或密码不对。登录失败统一用这个码，不细分是哪个错了。 |
| `USERNAME_TAKEN` | 409 | 否 | 用户名已被占用，换一个。 |
| `RATE_LIMITED` | 429 | 是 | 请求太频繁，或并发下载数已满。响应带 `Retry-After`，按它退避重试。 |
| `INTERNAL` | 500/502/503/504 | 通常是 | 提供 request_id 给管理员排查。 |

本设计早期规划过的一批错误码（`AUTH_REQUIRED`、`TOKEN_EXPIRED`、`PERMISSION_DENIED`、
`RESOURCE_NOT_FOUND`、`VERSION_ALREADY_EXISTS`、`PRECONDITION_FAILED`、`SYNC_CONFLICT`、
`SOURCE_UNREACHABLE`、`SOURCE_UNSUPPORTED`、`SECURITY_SCAN_FAILED`、`ARTIFACT_HASH_MISMATCH`、
`QUOTA_EXCEEDED`、`INTERNAL_ERROR`）**服务端一个都不发**。
对应关系是 `PERMISSION_DENIED`→`FORBIDDEN`、`RESOURCE_NOT_FOUND`→`NOT_FOUND`、
`ARTIFACT_HASH_MISMATCH`→`DIGEST_MISMATCH`、`VERSION_ALREADY_EXISTS`→`VERSION_CONFLICT`、
`INTERNAL_ERROR`→`INTERNAL`；v2 新增的 `SLUG_TAKEN` 与 `INVITATION_INVALID` 原本也没落表。
按上面那批规划码写分支，永远匹配不到——限流是 HTTP 429 + problem+json（`retryable` 字段），
不是独立错误码。

`RATE_LIMITED` 是例外：服务端确实发这个码（`ErrorCodes.RATE_LIMITED`），
用在两处——接口限流过滤器与下载并发上限（§4.1）。两处都返回 HTTP 429，
body 的 `retryable` 为 `true`，并带 `Retry-After` 头。

## 4.5 最小可交付范围（MVP）

MVP 只求端到端工作闭环：数据库与迁移、登录与 Skill 查询、Git 解析与安装、本地安装记录、
检查更新与回滚、私有云端备份与 changeset 幂等、敏感信息扫描与审计。七项已全部交付
（2026-11 核对）；随后追加的团队审批流、自动安全更新与多 Agent 适配器也已落地。

# 附录 A：开发实现注意事项

1. **§2.2 的清单是契约，不是自动生成的完整业务实现。** 清单与各 Controller 的实际路由必须一致；接口变化时同步更新客户端模型与契约检查。
2. **上传制品的临时态与正式态应分开。** 临时对象设置自动过期；正式对象按摘要寻址并禁止覆盖。
3. **同步 revision 不要直接等同于 Git commit。** 本地同步 revision 是 SkillMesh 的变更序号/摘要；Git commit 只表示上游仓库某一状态。
4. **不要通过覆盖原目录实现更新。** 使用 staging 目录、校验、原子替换和回滚点。
5. **不要把个人云端备份自动提升为可发现的市场版本。** 备份、草稿、已审核发布是不同状态。
6. **权限撤销后要停止新下载与同步。** 已下载到用户设备的文件无法被服务器保证瞬时远程擦除；客户端应在下一次联网时呈现撤回通知。
7. **第三方许可证必须保留出处和识别结果。** 自动识别结果不能替代法律判断；组织可配置不允许再分发的许可证策略。
8. **保持 Agent Adapter 可版本化。** 对每个 Agent 的目录、覆盖规则和 frontmatter 兼容性建立回归测试；不在业务服务中散落硬编码路径。
