## 修了什么

### 信任根与制品完整性

**1. CLI 钉住的验签公钥从未读进内存**（`apps/cli/internal/config/config.go`）

`Load()` 读了 server、client_id、network、agents，唯独没读 `verify` 段——
`cfg.Verify` 永远是零值，`Pinned()` 恒为 false。于是「注册中心换把钥匙」时，
本地那份钉住的公钥形同虚设，验签照样通过。信任根最关键的一环是断的。

改：`Load()` 把 `file.Verify` 读进来。加了回归用例
（`internal/config/config_test.go`：配置文件里的钉住公钥要读进来）。

**2. 签名与 `content_digest` 覆盖的是发布方自填的清单**（`UploadService.complete`）

服务端确实从真 zip 重算了逐文件清单（`ZipManifest.of`），但那份清单只进了
`artifacts.manifest_json`；**签名签的、对外发的 `content_digest`、审核面板列的文件清单，
用的都是发布方在建版本请求里自填的那份**。于是：

- 发布方声明「只有 SKILL.md、内容是 A」，真包里塞了别的文件，照发不误；
- 审核的人看到的是一份**假的文件清单**——审核队列那道闸就是这么被绕过的；
- 签名覆盖的是那份声明，不是包里真实的内容。

详细设计 §13 写的是「服务端必须重新计算归档内实际路径和哈希，并与上传声明比对」。
改：收尾时以服务端重算的清单为准（`version.setManifestJson(manifest)`），
签名、`content_digest`、审核面板全部对着真包；声明与真包不符**照收但记进审计**
（`manifest_mismatch`）。

> 这里没选「对不上就拒收」：仓库里有一条刻意的测试
> `声明的清单不可信要按真包算`（`ArtifactDiffServiceTest`），它就发布一份声明与真包
> 不符的版本并要求发布成功——仓库的既定立场是「不信声明、用真值」。改成拒收会把
> 这条测试和它的意图一起推翻，所以按仓库的立场来：真值覆盖 + 留痕。
> 加了回归用例 `声明的清单不可信时以真包为准`（`UploadArtifactTest`）。

**3. 同步回装不验签、不比摘要**（`apps/cli/internal/cmd/sync.go`）

`install` 那条路装之前会验签、会拿本地算出的摘要跟服务端 `content_digest` 对一遍；
`sync` 的下载回装**两样都没有**——下载回来的字节直接解包装进 Agent 目录。
改：补上同一道闸（`verifyArtifact`），验不过就不装。

### 越权与路径

**4. 安装目标目录名取自包里的 SKILL.md，且零校验**（CLI）

解包本身防了 zip 穿越（`installer.ExtractZip` 有 `checkEntryName` + `withinRoot`），
但**装到哪个目录**取自包内 `SKILL.md` 的 `name:` 字段，直接 `filepath.Join(base, name)`。
声明成 `../../..` 就能把文件写到 Agent 目录之外。

改：新增 `internal/cmd/skillname.go` 的 `checkDirName`（必须是单个路径段：
不含分隔符、不含 `..`、不是绝对路径、Windows 下不含 `:`），装/改/加三处统一走。
加了用例 `internal/cmd/skillname_test.go`。

**5. 路径穿越只记 warning，制品照发**（`ArtifactScanner`）

扫描器发现越界 entry 后只是记一条 finding，而 `isBlocking()` 只认 RULES 里的
「疑似凭据」类规则——「路径穿越」不在其中，于是结论是 warning，版本照发。
（顺带：那个 entry 的正文因为 `continue` 连密钥扫描都没跑。）

改：路径穿越改成阻断级。加了用例 `路径穿越要阻断`（`ArtifactScannerTest`）。

**6. 客户端上报的审计事件只判「看得见」**（`AuditReportController`）

任何登录用户都能往**别人**的 Skill 流水里塞「安装完成」这类条目，审计台分不出真假。
`source.policy_changed` 也在客户端可上报的白名单里——而这个类的注释自己写着
「特权事件由服务端自己记，客户端报上来的一律忽略」。

改：白名单去掉特权动作；上报条件从「看得见」改成「有关系」——属主、该组织/团队成员、
或真装过这个 Skill（有安装记录）三者之一。

**7. 安装流水里带本机绝对路径**（`InstallationController`）

审计台按 Skill 可见，谁看得见这个 Skill 就看得见这条流水——`C:\Users\alice\...`
就这么泄给了所有能看见 Skill 的人。改：流水里只留 agent 与版本，
绝对路径只留在安装登记表（只有本人可见）。

### 数据丢失

**8. 控制台连着编辑同一个版本，后一轮的改动被静默丢弃**（前端 + `VersionEditService`）

版本不可变，保存不是就地改，而是基于**源版本**重打包出一个新版本。前端抽屉的编辑
始终用「打开时的那个版本」当源：改一次产出 v1.0.1，再改一次还是基于 v1.0.0 →
产出 v1.0.2，里面**没有 v1.0.1 的改动**，面板却报「已保存为新版本」。

改：

- 前端（`FileBrowser.vue`）：抽屉自己记一个「编辑基准版本」，每次保存成功后推进到新版本，
  并重读文件内容；页面（`MySkillsPage` / `MarketPage`）跟着切到新版本并刷新版本表
  （市场页原先根本没订阅 `edited`，新版本在那页**完全不可见**）。
- 服务端（`VersionEditService`）：基于**旧于最新已发布版本**的底稿编辑 → 409，
  明确告诉用户最新的是哪一版。不这么拦，任何客户端都能悄悄产出丢改动的新版本。

加了用例 `第二次编辑基于新版本`（`apps/web/tests/browse.spec.ts`）。

### 资源耗尽

**9. 制品大小上限在整包读进堆之后才检查**（`ArtifactService.promote`）

预签名地址在有效期内还能继续 PUT，对象可能比声明的大得多；原实现先把对象整个读进堆
再比大小。改：先 `stat` 问大小（超了直接拒），读的时候也**有上限地读**。

**10. 扫描器与清单读解压项没有边**（`ArtifactScanner.readEntry`、`ZipManifest`）

两个地方都是「先整个读进内存，再看超没超限」——一个 500MB 的解压项就能把堆撑爆，
那时再判断已经没意义了。改：边读边卡上限；清单再加一道单文件 20MB 上限
（与扫描器同一个数，两边口径一致）。

### 状态机与并发

**11. 撤回了的版本能被重新送审**（`ReviewService.submit`）

撤回的约定是「不可逆，要恢复得发新版本」，但撤回后的版本还能被重新送进审核队列，
过审就又变成已发布。改：撤回/下架状态直接 409。

**12. 撤回了的版本能被上传会话转成已发布**（`UploadService.complete`）：同上，409。

**13. 撤回没有制品的版本会变成 500**（`SkillVersionService.revoke`）

DDL 的 check 约束要求 revoked 的版本必须有制品，没有制品还去撤就撞约束。
改：409 + 说清楚「没有东西可撤回」。

**14. 发版不锁 `skills` 行，`latest_version` 会丢失更新**（`UploadService` / `ReviewService`）

两个并发发布各读各的 `latest_version`，后写的把先写的顶掉——latest 退回旧版本。
改：加 `findByIdForUpdate` 行锁，锁的顺序统一为「先版本行、后 Skill 行」（避免死锁）。

**15. 不存在的 Skill 的审计接口返回 500**（`AuditController`）：改 404。

`publish` 从不带来源元数据（从 Git 装的 Skill 发布后被记成 `local_import`，

### 一处**审计误判**的更正：ID-5（审核放行的角色作用域）

原报告说「审核放行的角色作用域固定取 `owner_team_id`，与团队治理文档『组织范围的版本只有组织角色这一层』不符」。
复核后：**这是误判**。[团队治理.md:52](团队治理.md#L52) 写的正是代码的行为——

的语义就是「有团队成员行用团队角色，没有才回落组织角色」。

但顺着这条线查出了**一个真的缺口**：`owner_team_id` 若被挂到组织可见的 Skill 上，
审核作用域就会落到团队角色上，与文档不符。改：`ReviewService` 与 `ReviewQueueService`
里团队作用域只在 `visibility == "team"` 时才用（[ReviewService.java:112](https://d/dev/MyProject/SkillMesh/apps/api/src/main/java/com/skillmesh/api/review/ReviewService.java)、
[ReviewQueueService.java:118](https://d/dev/MyProject/SkillMesh/apps/api/src/main/java/com/skillmesh/api/review/ReviewQueueService.java)）。

| **`users.status` 没人能改** | 组织 owner/admin 可以禁用/启用本组织成员（`PATCH /organizations/{id}/members/{uid}` 收 `status`）；**禁用立刻生效**——`CurrentUserService.current()` 是所有请求的强制点，被禁用的账号在那里就被拒。另有两条更严的：不能禁用自己的账号、不能禁用组织 owner（owner 是组织的最后一道保险） |

### 补审：性能方向（第一轮整路没审，第二轮单独跑了一遍）

先量了底：远程 PostgreSQL **单次往返实测 57.3ms**（50 次单行 SELECT 均值）。
库在远端，N+1 的每一次查询都是 57ms 的墙钟时间——查询条数直接等于用户等待时间。
线上现状：单个 Skill 最多 20 个版本、单组织 25 份邀请。

| 位置 | 问题 | 改后 |
| --- | --- | --- |
| 版本详情 | 顺带调了版本列表，把该 Skill 的**全部版本**连同制品与扫描都查了一遍 | 46 → 5 次查询 |
| 版本列表 | 循环里逐个查制品、逐个查扫描 | 43 → 5 次查询 |
| 审核队列 | 每条待审版本查 skills/scans/sources/users 各一次（4N） | ≈152–202 → 5 次查询 |
| 邀请列表 | 每条邀请查一次组织、一次团队 | 51 → 3 次查询 |

改法都是「一次批量查齐 + 循环里只拼装」，没引新依赖。
用例用 Hibernate 的查询统计数条数（新增 `support/QueryCounter`），四条用例分别钉住这四处。

### 补审：同步与安装方向（第一轮整路没审，第二轮单独跑了一遍）

查出三个真问题，其中一个会**丢用户改动**：

1. **同步基线被写成本地当前内容**。基线是「双方共识的那份内容」，不是「本地现在是什么样」。
   写歪了有两个后果：一次「无变化」的同步就把逐文件摘要与内容副本清空，之后两边同改就再也合不了；
   更糟的是——本地领先云端时跑 `skillmesh sync --direction download`，下一轮会把
   「本地领先」误判成「本地落后」，**把云端的旧版装回本地，覆盖掉用户的改动**。
2. **`mergePlan` 把「本机删掉、云端还在」的文件从云端拉回来**。函数自己的注释写着
   「本机删掉的文件不在结果里，删除传播要人确认」，代码却当它是「云端新增」拉回来——
   用户的删除被静默撤销，还跟着合并结果一起上传回云端。
3. **服务端出错被报成「冲突」**。服务端的契约是「冲突 = 响应里 status == conflict」，
   其余（500/404/403）都是失败；报成冲突会让用户去跑 `--resolve`，而且因为 outcome
   不是 failed，这次上传也不进重试队列。

三处都修了，并补了四个用例（基线不清空、方向过滤不动基线、服务端出错不当冲突、
本机删掉的文件不从云端拉回）。

### 仍然没做的

- **多用户下的审计上报权限测试**：已补（`AuditReportPermissionTest`，用 realm 里的 `dev-user2`）。
- **发版并发的用例**：已补（`ConcurrentPublishTest`）。
- **性能方向与同步安装方向**：第二轮各派了一个 agent 单独审，结论见下。

## 没修的（复核过，确实存在）

第一、二轮列的遗留已分别在上面两节处置；第三轮又做掉 12 项，下面这些是**三轮做完仍然在的**：

| 问题 | 为什么没动 |
| --- | --- |
| 桶里**已经存在的**历史孤儿对象不会自动清掉 | 本轮修的是「不再产生新的孤儿」（内容寻址，同一 sha256 只写一次）。清理存量要写一次性脚本或加非 `tmp/` 前缀的生命周期规则，那是运维动作 |
| `artifacts.record()` 并发插入撞 `sha256` 唯一约束会变成 500 | 改动前就有的行为。修它要给 `record` 加冲突重读（需要新事务/重试），改动面大；本轮没让它变差 |
| 同步写入的基线前置条件只卡在「建版本」那一步 | `[建版本, complete]` 这段窗口没覆盖：窗口里别的设备发布了不会被拦。要补得把基线存到版本行（新增列 + 迁移） |
| 「本地删除」要显式 `--allow-delete` 才传播 | 设计文档 §6.4 说「删除传播：软删除、回收期、支持恢复」，本轮只做到「不静默传播 + 要人确认」；回收期与恢复是另一项功能 |
| 合并后目录里的符号链接会丢失 | 临时副本用 `installer.copyTree`，它只拷普通文件。符号链接本来就不在同步模型里（`packager.Pack` 与 `skillscan.DirHashes` 都不认），但从「保留」变成了「合并后消失」 |
| 合并要把本机目录拷两遍 | 「临时副本上合并 + 原子换入」的固有代价。带 `.git` 的大目录会明显变慢 |
| 邀请列表的索引没跟上排序键 | `V4__invitation_list_index.sql` 建的是 `(organization_id, created_at DESC)`，分页排序键多了 `id`，PG 只能增量排序。要最优得 `(organization_id, created_at DESC, id DESC)`，补一次迁移 |

## 文档与实现的差距

- 详细设计 §13 要求「服务端重新计算并与上传声明比对」——**原先根本没比对**（已修）。
- 部署文档说「换成企业 IdP，代码不用改」——前端原先**写死**了 issuer 与 client_id（已修：新增公开配置端点）。
- 设计文档 §14 说「没登录的按来源 IP 限」——受保护接口上**限流器根本轮不到执行**（已修：挪进鉴权链）。
- 团队治理文档说「组织范围的版本只有组织角色这一层」——代码**本来就是**这么做的（审计误判），
  但 `owner_team_id` 挂到组织可见的 Skill 上会让审核作用域跑偏（已修）。
