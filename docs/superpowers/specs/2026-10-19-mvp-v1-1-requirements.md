# SkillMesh MVP v1.1 需求（JTBD 拆解）

> 日期：2026-10-19 | 状态：待确认范围 | 上游：[设计文档](../../设计文档.md) §15 阶段划分、[MVP v1 设计](2026-10-19-mvp-v1-design.md)

## 这一阶段要解决的

MVP v1 已经把「注册中心 + Git 来源 + CLI 全套命令」跑通了。剩下来的需求分两类：**单人自用会立刻撞上的**，和**要建团队治理才能用上的**。这一阶段只做前者，daemon 同步与团队治理整体推到 v2。

判据很简单：**不需要第二个人参与就能用上的，进这一阶段；需要组织、审批、角色才能用上的，推 v2。**

## 现状盘点（2026-10-19 实测）

已具备：搜索/详情/版本列表、Git 来源解析与安装（`add --all`）、`update --check`、注册中心安装、`publish`（版本累加、slug 取目录名）、`rollback`、一次性 `sync`、客户端密钥扫描阻断、Claude Code / Codex 适配器、原子安装与锁文件。

对照设计文档仍缺（按 §15.1 验收用例核对）：

| 设计文档要求 | 现状 |
| --- | --- |
| §3.3 更新时做文件级差异比较 | 只报 commit 变了，没有差异 |
| §3.2 展示来源、作者、commit、许可证、风险提示 | 只在 add/install 打印一行许可证，无来源与风险面板 |
| §3.1 其他设备登录后可恢复个人 Skill | 没有「装回我自己的全部 Skill」的入口 |
| §10 撤回：改变可用状态并提示客户端 | 没有 revoked/yanked 的客户端提示 |
| §10 审计：记录发布、审批、下载、安装、升级 | audit_events 表在，无写入 |
| §10 内容扫描：扫描记录与状态 | 只有客户端扫描，服务端 skill_scans 空着 |
| §6.3 冲突策略 | 无 |
| §6.2 离线队列与重试 | 无 |
| §3.1 本地 Daemon 监听 | 无（sync 是一次性扫描） |

## 故事

### S1 看懂一次更新到底改了什么

**描述**：当我要更新一个装着的 Skill 时，我想看到新旧两版之间具体改了哪些文件、哪些行，而不是只看到一个 commit 短哈希，这样我能在覆盖本地内容之前判断值不值得。

**验收标准**

1. `skillmesh update <name> --dry-run` 输出变更文件清单：新增 / 修改 / 删除三类分开列，每行带相对路径。
2. 修改的文件给出行级摘要（增删行数），不给完整 diff；超过阈值（建议 200 行）只报统计。
3. 本地相对已安装版本有未提交修改时，明确提示「本地有改动，保留本地版本」，不自动覆盖。
4. 有本地改动时不覆盖，`update` 退出码为 0 并把该 Skill 标为「已跳过」，其余 Skill 照常更新。
5. 拿不到差异（远端已删文件、网络失败）时退化为只报 commit，不中断整批更新。

### S2 装之前知道这份 Skill 从哪来、有多危险

**描述**：当我要把一个第三方 Skill 装进我的 Agent 时，我想一眼看到它的来源仓库、作者、许可证、最近一次扫描结论和已知风险，这样我能判断要不要装进工作环境。

**验收标准**

1. `skillmesh info <id>` 输出：来源类型与仓库 URL、解析到的 commit 或版本、许可证识别结果、最近扫描状态与命中规则。
2. 来源信息缺失时逐项显示「未提供」，不留空字段让人猜。
3. `install` 在装之前打印同样的风险摘要；命中密钥扫描时**提示但不阻断**（本地是用户自己的机器），并指出文件与行号。
4. `publish` 时把客户端扫描结论一并上报，服务端落进 `skill_scans`；这属于 S5 的最小形态。
5. 风险摘要与实际装的那一份来自同一个制品（按 artifact id 取，不按 Skill 取），避免张冠李戴。

### S3 换了设备能把个人 Skill 装回来

**描述**：当我在新机器上登录 SkillMesh 时，我想一次性把我个人私有空间里的 Skill 装回本机，这样不用一个个搜、一个个装。

**验收标准**

1. `skillmesh search --mine` 只列我名下的 Skill（public 的团队 Skill 单独用默认搜索）。
2. `skillmesh restore`（或 `install --mine --all`）把选中的 Skill 按最新已发布版本装到指定 Agent 与作用域。
3. 单个 Skill 失败不中断整批，结束时给出成功/跳过/失败三段汇总。
4. 目标目录已有同名且不受 SkillMesh 管理的目录时跳过并说明，不静默覆盖。
5. 整个流程写锁文件，`list` 能列出这批安装，CI 的 `--locked` 可用。

### S4 出事了能把版本收回来

**描述**：当某个已发布版本被发现有问题时，我想把它标记为撤回，让之后安装的人看到警告，同时不静默删掉已经在别人机器上的内容。

**验收标准**

1. `POST /api/v1/skills/{id}/versions/{v}/revoke`（仅版本所有者或组织管理员）把状态置为 `revoked`，记录原因与操作者。
2. `search` / `info` 对含 revoked 版本的 Skill 显示撤回标记；`install` 该版本时**拒绝并给原因**。
3. 已安装的用户在 `update --check` 或 `list` 时收到一次提示，指向撤回原因；不自动卸载、不删本地文件。
4. 撤回是可审计事件（S6）。
5. 撤回不影响同 Skill 的其他版本，也不可逆（要恢复得发新版本）。

### S5 上传的内容在服务端也过一遍扫描

**描述**：当我要把 Skill 发布到团队可见的范围时，我想服务端也独立扫一遍，而不是只信客户端那端的检查，这样绕过 CLI 的上传路径也不会漏。

**验收标准**

1. `complete` 校验通过后，服务端解包跑扫描规则，结论写入 `skill_scans`（scanner_name、scanner_version、findings_json、status）。
2. 扫描命中密钥或路径穿越时，版本状态置 `quarantined`，不进入 `published`，响应里带上命中规则。
3. 扫描是同步的，超时（建议 30s）按「未完成」处理并标记，不阻塞其他 Skill。
4. 扫描规则与客户端同源（同一份规则清单），版本号不同、内容一致，便于对照。
5. `info` 能查到该版本的扫描结论与时间（S2 的数据来源）。

### S6 谁在什么时候动了什么

**描述**：当团队里出了「谁把哪版发上去的」「谁下载了什么」，我想有一条不可篡改的流水，而不是靠翻聊天记录。

**验收标准**

1. 发布、撤回、安装、下载、卸载、权限变更写 `audit_events`（actor、action、target、result、metadata、时间）。
2. `POST /api/v1/audit/events` 只接受**客户端可上报的少量事件**（如安装完成、离线失败重试成功），服务端特权事件不接受客户端上报。
3. `GET /api/v1/skills/{id}/audit` 只对有权限的人开放，返回按时间倒序的分页列表。
4. 日志与审计里不出现令牌、私钥、Skill 全文。
5. 审计写入失败不阻断主流程，但要留下可查的失败记录。

## 明确推到 v2（不在这一阶段）

| 需求 | 文档出处 | 为什么不进这一阶段 |
| --- | --- | --- |
| 本地 Daemon、文件监听 | §3.1、§5 | 常驻进程 + 跨平台监听是独立子系统，收益要等 S1–S6 落地后才显现 |
| 离线队列与指数退避重试 | §6.2 | 需要 S3 的批量恢复跑通后才值得做队列 |
| 双设备冲突处理与三方合并 | §6.3 | 需要 sync_states 基线模型，先有第二个设备才有真实冲突 |
| 组织 / 团队 / 角色矩阵 | §10 | 没有第二个人时无人消费 |
| 发布审批流 `draft→scanning→pending_review→published` | §10.1 | S5 的扫描结果就是审核的输入，先有扫描再谈审批 |
| 制品签名与供应链证明 | §10 | 需要先有稳定的 manifest 摘要口径 |
| Cursor 适配器 | §8 | 适配器是配置驱动，加一个 Agent 不改核心模型 |
| 限流、SSRF 主机白名单、制品大小配额的生产化 | §14 | 当前是内网单机；对外暴露前必须做 |

## 阶段验收

这一阶段算完成的标志（对应设计文档 §15.1 中尚未覆盖的用例）：

- 我能看到一次更新改了哪些文件，且本地有改动时不会被覆盖。
- 任何一份 Skill 在装之前能看到来源、许可证、风险与扫描结论。
- 我能在新机器上一条命令装回我自己的全部 Skill。
- 被撤回的版本装不上，已装的用户会收到提示。
- 绕过 CLI 的上传也会被服务端扫描拦下。
- 发布、下载、安装、撤回都有审计流水，且不含凭据。

## 落地状态（2026-10-20）

| 故事 | 状态 | 说明 |
| --- | --- | --- |
| S3 换设备装回 | ✅ | `search --mine` + `restore`；服务端加 `?mine=true` |
| S1 差异预览 | ✅ | `update <name> --dry-run` 输出文件级差异；`installed_hash` 判定本地改动并保护 |
| S2 风险面板 | ⚠️ 部分 | `info` 展示来源/扫描/风险、`install` 装前提示扫描结论；**「来源=仓库 URL / commit」在注册中心侧拿不到**——v1 没有任何地方往 `skill_sources` 写，Git 来源信息只在本地锁文件里 |
| S5 服务端扫描 | ✅ | 解包扫描写 `skill_scans`，命中即 `rejected`；扫描规则与客户端同名同序 |
| S4 撤回 | ✅ | `POST /skills/{id}/versions/{v}/revoke`；`list` 警告、`install` 拒绝；DDL 的 `revoked` 状态无 `quarantined`，阻断时用 `rejected` |
| S6 审计 | ⚠️ 部分 | 发布/撤回/下载写 `audit_events`，`GET /skills/{id}/audit` 可查；**安装与卸载发生在客户端，没有上报通道**，按 S6-AC#2 的边界处理 |

偏离说明：

1. S2-AC#4 原写「客户端扫描结论一并上报」。改为**服务端独立扫描为准**——客户端结果只做本地提示，上报两份可能不一致的结论没有意义。
2. S6-AC#2「客户端可上报的少量事件」没有实现：`POST /api/v1/audit/events` 留到真有离线场景再说（离线队列本身在 v2）。

## 顺序建议

S3 → S1 → S2 → S5 → S4 → S6。

S3 最便宜（几乎是 `search --mine` + 批量 install）且立刻有感；S1 需要差异算法但价值直观；S2 是 S5 的展示面，先把数据（manifest、扫描）落下来再做 UI；S4/S6 依赖 S5 写入的数据结构。
