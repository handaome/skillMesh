# 团队控制台使用手册

> 面向第二个人加入团队之后的日常操作：登录、邀请、发布到团队、审核、安装。

控制台是浏览器里的页面，发布与安装走 CLI。
起环境见 [README](../README.md#快速开始)，CLI 全部命令见 [CLI 使用手册](cli-使用手册.md)，概念与角色见 [团队治理与安全](团队治理.md)。

## 1. 登录

浏览器打开控制台首页（`http://127.0.0.1:5174`）。没登录会被带到登录页，点「登录」跳到 Keycloak 完成认证后回到控制台。

- 令牌存在浏览器 localStorage 里，有效期一年（Keycloak realm 的 `accessTokenLifespan: 31536000`）；期间由 `ensureFresh()` 静默续期，过期了会自动跳登录页。
- 登出在右上角。

## 2. 建组织与团队

组织是顶层空间，团队是组织下面的一组人。Skill 的可见性有四档：

| 可见性 | 谁能看 |
| --- | --- |
| private | 只有属主 |
| team | 该团队的成员，或该组织的 owner/admin |
| organization | 该组织的成员 |
| public | 所有人 |

建组织和建团队目前用 API（CLI 还没有这两个命令）：

```bash
TOKEN=$(curl -s -X POST "http://127.0.0.1:8180/kc/realms/skillmesh/protocol/openid-connect/token" \
  -d "grant_type=password" -d "client_id=skillmesh-test" \
  -d "username=dev-user" -d "password=dev" \
  | python -c "import sys,json;print(json.load(sys.stdin)['access_token'])")
ORG=$(curl -s -X POST http://127.0.0.1:8080/api/v1/organizations \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"slug":"acme","name":"Acme"}' | python -c "import sys,json;print(json.load(sys.stdin)['id'])")
curl -s -X POST "http://127.0.0.1:8080/api/v1/organizations/$ORG/teams" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"slug":"platform","name":"Platform"}'
```

这段用 `python` 解析 JSON。机器上没有 `python`，就把两处 `python -c` 换成 `jq -r .access_token` 和 `jq -r .id`。

建组织的人自动是 owner；建团队、发邀请都要 owner 或 admin。

团队页的成员表改的是**哪一层的角色**，取决于有没有选团队：**选了团队**改的是这个团队里的**团队角色**（团队没有 owner 这一档），**不选团队**改的是**组织角色**（多一档 owner）。两层角色各管各的事——发布权看组织角色，审核放行权看团队角色，见 [团队治理](团队治理.md)。

## 3. 邀请成员

团队页 → 「邀请」区 → 选团队和角色 → 点「生成邀请链接」。

- 只有组织的 owner / admin 能发邀请。
- 链接 7 天内有效，库里只存哈希，明文只显示一次。
- 把链接发给对方；对方打开后登录并点「接受邀请」即入组。
- 发出后还能在列表里撤销。

## 4. 发布到团队

先用 `skillmesh login` 登录 CLI（见 [CLI 使用手册](cli-使用手册.md)），再发布：

```bash
skillmesh publish ./skills/java-debug --org acme --team platform
```

- `--org` / `--team` 传的是 **slug**，不是 id。
- 给了 `--team` 时可见性是 team，只给 `--org` 时是 organization。
- 发布权看的是**组织角色**：你在组织里要 publisher 及以上才能发。受邀入组默认是 member——要发到团队，让管理员在团队页**不选团队**时把你的组织角色提到 publisher。
- 团队与组织可见的版本**不会直接发布**，会停在待审核状态。

## 5. 审核

「审核」页列出待审版本。点进去能看到：

- 扫描结论与服务端扫描命中的规则
- 来源（仓库、分支、commit）
- 与上一个已发布版本的文件级差异（新增/修改/删除 + 增删行数）
- SKILL.md 正文

差异大到只报文件级时，页面会明说「差异较大，只报文件级」。

reviewer 及以上角色才能看到并处理自己范围内的待审版本——这里看的是**团队角色**（团队里没有你的成员行时才回落到组织角色）。发布权则看**组织角色**，两层别混：见 [团队治理](团队治理.md)。

## 6. 安装

审核通过后，团队成员就能装：

```bash
skillmesh search java-debug
skillmesh install <skill-id>
```

`search` 输出的最后一列是 Skill 的完整 ID，把它喂给 `install`。

团队可见的 Skill，该团队的成员与该组织的 owner/admin 能搜到并下载。

## 7. 排错

| 现象 | 原因 |
| --- | --- |
| 登录页报「登录状态校验失败」 | state 对不上，重新点一次登录 |
| 邀请页显示已失效 | 超过 7 天或已被撤销，重新生成 |
| 看不到待审版本 | 你在这个范围的**团队角色**不到 reviewer 及以上——你在该团队里有成员行时看那行，没有则回落到组织角色。改哪一层：控制台里**选中该团队**改的是团队角色，**不选团队**改的是组织角色（见 [团队治理](团队治理.md)） |
| CLI 报「组织 xxx 不存在或你不是成员」 | `--org` 传的是 slug；用 `skillmesh` 登录的账号不在这个组织里 |
| CLI 报「你在组织 "xxx" 的角色是 member，发布到组织/团队需要 publisher 及以上」 | 发布权看的是**组织角色**——让组织管理员把你的**组织角色**提到 publisher（控制台里不选团队时改的就是组织角色） |
